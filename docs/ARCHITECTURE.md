# Architecture

Headless core, thin UIs, everything extensible through one plugin API.

```
kassensturz/
├── CMakeLists.txt                  # builds and installs the app; drives Cargo (D-063)
├── Cargo.toml                      # workspace root
├── crates/
│   ├── kassensturz-core/           # domain model + logic; no UI, no I/O specifics
│   │   ├── money                   # 64-bit integer minor units + ISO 4217 code; amount × ratio and amount × or ÷ rate, rounded once (D-027, D-051)
│   │   ├── rounding                # rounding modes; the book stores which one it uses (D-027, D-078)
│   │   ├── account                 # accounts (incl. credit cards), categories, payees
│   │   ├── transaction             # double-entry transactions + splits (Parts): no category yet, foreign amounts, what a bank delivered; the remainder (D-083)
│   │   ├── transfer                # Transfer matching between the user's own accounts, and joining both sides into one transaction (D-021, D-087)
│   │   ├── currency                # ISO 4217 codes and KassenSturz's own ISO 4217 table, read from data/ (D-062, D-077); a currency with its decimal places in a book
│   │   ├── decimal                 # exchange rates, prices and quantities as fixed-point decimals, rust_decimal kept private (D-051, D-079)
│   │   ├── rates                   # exchange rates on a date: the rows of the book's price table, entered by hand (D-028)
│   │   ├── budget                  # basic budgets: a monthly limit per category (D-029)
│   │   ├── rules                   # auto-categorization: conditions, actions, Rule tree with sub-Rules
│   │   └── events                  # event bus (TransactionAdded, ...)
│   ├── kassensturz-store/          # all SQLite code: store, migrations, backups, change history — see D-016, D-032, D-033, D-072
│   ├── kassensturz-import/         # the Importer interface, statements and limits for untrusted files (D-091); CSV, OFX, MT940, CAMT.053, KMyMoney (.kmy / SQLite)
│   ├── kassensturz-export/         # the Exporter interface, the data an export is made from, and the formats it writes: CSV (D-099) and the complete export of a book, which it also reads back (D-100)
│   ├── kassensturz-pipeline/       # the import pipeline: statements into an account, with the duplicate check, Transfer suggestions, Rules and the balance check (D-030, D-092); gathering a book's transactions or the whole book for export, filling a new book from a complete export (D-099, D-100), and filling one from another program's book, such as KMyMoney's (D-101)
│   ├── kassensturz-bank/           # read-only bank connections: the Bank trait, IBAN → bank setup, PIN session, fetched data → Statement, fake bank for tests — see D-053, D-060, D-145, D-146
│   ├── kassensturz-aqbanking-sys/  # raw AqBanking/Gwenhywfar declarations (bindgen, committed, loaded at runtime) — see D-060; gwengui/ holds the C++ library for Gwenhywfar's Qt dialogs (Q-035)
│   ├── kassensturz-plugin-api/     # stable, versioned plugin interface (after 1.0, D-071)
│   ├── kassensturz-plugin-host/    # loads and sandboxes WASM plugins (D-007; after 1.0, D-071)
│   ├── kassensturz-platform/       # keychain, config paths, notifications behind traits
│   ├── kassensturz-charts/         # the chart model types of the ChartProvider boundary (text labels, drawing values, text table; no Qt) — D-276; KQuickCharts itself is a QML module (D-275)
│   ├── kassensturz-report/         # the report designer's reporting layer: read-only datasets, periods, filters, exact totals, calculated metrics, the dashboard document and its limits (M6, D-277, D-278)
│   ├── kassensturz-ai/             # LLM provider abstraction (OpenAI-compatible adapter in v1), consent, redaction
│   ├── kassensturz-ai-chat/        # the chat: the loop of the read functions with a provider, the number check, the tool-call log, the fake model (D-190)
│   ├── kassensturz-ai-tools/       # the fixed list of read functions the AI may call, the overview, the number check, change sets (D-170); shared by chat and MCP
│   ├── kassensturz-mcp/            # local MCP server for the user's own AI tools: the read functions of kassensturz-ai-tools over stdio, read-only unless its write tools are on (D-194 to D-197, D-216 to D-219)
│   ├── kassensturz-receipts/       # post-1.0: OCR + transaction-matching for photographed/scanned receipts
│   ├── kassensturz-mobile-bridge/  # post-1.0: Rust↔Kotlin FFI exposing core+receipts to the native Android app — see D-019, Q-018
│   ├── kassensturz-sync/           # post-1.0: shared-host ↔ thin-client access for multi-user (Member-scoped) — see D-022, Q-021/Q-022
│   ├── kassensturz-cli/            # CLI front end for testing the core and the store: English only, errors as codes, not installed (D-085)
│   └── kassensturz-ui-bridge/      # the desktop app: cxx-qt bindings exposing the core to QML
│       ├── qml/                    # Kirigami UI, one file per screen: overview, register, reports, settings, plugins
│       └── cpp/                    # small C++ helpers: the window icon (D-165), Qt's locale data for formatting (D-065), KConfig for the app's settings (D-112), what Qt knows about the computer
├── data/                           # desktop file, AppStream metadata and the app icon (icons/, D-165)
├── po/                             # translations, one folder per language (D-034)
├── plugins/examples/               # sample importer, report, automation (after 1.0)
├── packaging/                      # flatpak/ (manifest and its offline crate list), windows/, macos/
├── tools/                          # sdk.sh: runs commands in the build environment (D-063); update-currency-table.py (D-077)
├── docs/
└── .github/
```

## Build and development

- CMake (with KDE's Extra CMake Modules) drives Cargo: Cargo builds the Rust crates, CMake installs the desktop file, AppStream data, icons (`data/icons/`, D-165) and translations (D-063).
- Development, CI and the Flatpak use one environment, the KDE Flatpak SDK with the Rust extension; Flatpak builds use vendored Cargo dependencies (D-063).
- `tools/sdk.sh <command>` runs any command in that environment, e.g. `tools/sdk.sh cargo test --workspace`; CI uses the same script. Versions are pinned in D-073.
- Two more CI jobs lint and test every crate except the app crate, one on Windows and one on macOS, with `rustup` installing the same Rust version; the Qt builds on Windows and macOS come with their packaging (M7, D-090).
- A `kubuntu` CI job builds, tests and starts the whole app, Qt part included, on Kubuntu 26.10 from the distribution's own Qt, KDE Frameworks and SQLite (installed with `-DCMAKE_INSTALL_PREFIX=/usr` into a staging folder), as groundwork for a `.deb` next to the Flatpak. Kubuntu 26.10's KDE Frameworks 6.29 is the minimum in `CMakeLists.txt` (D-094).
- A `fedora` CI job does the same on Fedora 44, the current stable release, from Fedora's own packages, as groundwork for an RPM (D-097).
- CI runs the quick checks (REUSE, DCO, licenses, formatting) first and the slow jobs after them, keeps Cargo's downloads and build output between runs and skips the slow jobs for pull requests that only change documentation (D-110).
- CMake runs `cargo build --locked` as a custom target, as KDE's guide does, and installs the program it builds. QML files live in `crates/kassensturz-ui-bridge/qml/` because cxx-qt-build registers QML files by their path inside the crate.
- The Flatpak manifest (`packaging/flatpak/`) builds offline from `cargo-sources.json`, which is regenerated from `Cargo.lock` whenever that changes (`README.md`, "Building").
- CMake also builds `kassensturz-gwengui` (`crates/kassensturz-aqbanking-sys/gwengui/`), the small C++ library around Gwenhywfar's Qt 6 dialogs (Q-035, D-140), when pkg-config finds `gwengui-qt6`; without it the app builds and runs without bank dialogs (D-054). The library is installed under `lib/kassensturz/` and loaded at runtime, like AqBanking itself; its test runs under `ctest` in the Kubuntu and Fedora jobs. The Rust declarations in `kassensturz-aqbanking-sys` are regenerated only when AqBanking is upgraded, with `bindgen/generate.sh` (D-060, D-138).
- The first code is a walking skeleton through every layer, kept as real code (D-068). Since M1.M the app opens with the first-run mock instead of the skeleton's sample account (D-089); since M3.4 the first start is real (D-116), since M3.5 the register and the transaction page are (D-118), and since M3.9 the overview is (D-122), which ends the mock.

## The app's screens (M3)

- The first-run mock (M1.M, D-068, D-089) tested the simplicity goal (AGENTS.md §1, §6) before the real screens: welcome, add an account, add a transaction, see the overview. The real screens replaced it piece by piece, the overview last (M3.9), so the mock is gone; the notice that this is an early test version stays on the first-run pages (`MockNotice.qml`).
- `kassensturz-ui-bridge/src/overview.rs` reads the overview (M3.9, D-122): the open accounts per currency as `accounts::view` lists them, one month's parts booked to categories or to none yet through `Book::transactions_between`, added up per currency from the exact amounts in the currency the transaction counts in (D-043), with money moved between the user's own accounts and starting balances left out (D-021); the newest five transactions across the accounts, from `register::entries`, a Transfer once. `Month` steps through the calendar, and `Book::booking_date_range` says how far. `src/overview_model.rs` is its QML object, `BookOverview`, which keeps the month shown; the lists go to QML as lists of maps of text, which QML views take as models.
- `kassensturz-ui-bridge/src/export.rs` saves a copy of the open book (M3.12, D-125): `save_csv` gathers the transactions of the ticked accounts with `export_transactions` and `save_book` the whole book with `export_book`, both written by `export_file` into a new file; `CsvForm` turns the user's choices (usual ones from the region's decimal mark) into `CsvExportSettings`. `src/book_from_file.rs` reads a complete export, a `.kmy` or a KMyMoney SQLite file (`read`, recognized by its start, a `.ksz` or a bank statement told apart), turns the user's typed answers about currencies no table lists into `Replacement`s (`replacements`, `parse::read_rate`), and fills a book (`fill`, `fill_book` or `fill_book_from`). `books.rs` `Books::create_filled` makes the new book in the data folder, fills it and only then remembers it, or removes it again. `export_model.rs` (`DataExport`) and `book_from_file_model.rs` (`BookFromFile`) are the QML objects; `BookFromFile` fills the open book if `Book::is_empty`, otherwise it opens a new one and `BookSession.adoptOpenBook` shows it.
- `src/parse.rs` reads typed amounts in the user's regional format (D-065); `src/register.rs` writes an account's register and balances, a debt as "You owe" (D-067), sorts the entries and adds up the balance after each one from the exact amounts (D-118).
- `src/register_model.rs` is the register's QML object, `AccountRegister`: a `QAbstractListModel` whose rows live in Rust, so the view asks only for what it shows; `src/transaction_entry.rs` behind it adds, changes and removes a transaction from the register's page (M3.5): only a simple one, one account and one category or none, can be changed there (D-118).
- `src/parts_entry.rs` breaks a transaction down into Parts (M3.6, D-119) behind `PartsPage.qml` and `PartRow.qml`, on the same QML object: `details` shows the transaction with its last Part open, `preview` works out the open Part (`Transaction::remainder`), the amounts in other currencies (`Book::convert` where the book has a rate) and what is missing or too much, all from the exact amounts, and `save` replaces the transaction through `Transaction::new`, so it can't stop adding up. Parts booked to another of the user's accounts are kept as they are.
- `src/transfer_prompt.rs` writes the Transfers `Book::transfer_suggestions` finds as text for `TransferPrompt.qml` (M3.7, D-120), on the same QML object (`transferSuggestions`, `joinTransfer`): the account names, the dates and other parties the two accounts show (D-108) and the amount in the user's format. `join` calls `Book::join_transfer` only for a pair the book suggests right now. The transaction page asks after saving a transaction that is one side of a suggestion; the import (M3.10) uses the same dialog with all suggestions.
- `src/rules.rs` is the Rules screens as they read the book (M3.11, D-124): `view` lists the Rules in order with their depth and place among their neighbours, `RuleForm` and `ConditionForm` are the editor's text-and-flags form (`form_of`, and `rule_of` back into a core `Rule`, amounts typed without a sign next to a direction), `add_rule`, `change_rule` (with or without sorting again what the Rule sorted before, `preview_rebook` first), `remove_rule` and `move_rule` call the store's Rule actions (each one user action), `form_from_transaction` and `form_from_suggestion` start a Rule from what the user has, and `suggestions` counts what the user sorted by hand (`SUGGEST_AFTER` times, D-071) with the turned-down ones kept in the app's settings (`dismissed`, `dismiss`). `src/rules_model.rs` is the QML object `RuleBook` over it; `RulesPage.qml`, `RulePage.qml` and `RuleCondition.qml` are the screens, the register page shows the suggestion and the transaction page offers "Create a Rule from this transaction…".
- `src/statement_import.rs` is the import of a bank's file into one account as the screens see it (M3.10, D-123): `recognize` judges a file by its start and name among the importers of `kassensturz-import` (never the test format), `CsvForm` turns the column screen into `CsvSettings` and back and keeps a bank's settings in the app's settings (`csv_banks`, `save_csv_bank`), `Loaded` holds the file's statements with the user's choices (which statement, which lookalikes to import anyway), `preview` runs `kassensturz-pipeline`'s `import_statements` inside `Book::dry_run` and `import` runs it as the user action, both described as text: every entry's outcome and category, the counts, the bank's opening and closing balances against `Book::balance_on`. A matching closing balance is kept as the stated balance (D-117) in the same action. `src/statement_import_model.rs` is its QML object, `StatementImport`, whose `step` names the next page: `ImportStatementsPage.qml`, `CsvSettingsPage.qml` (with `CsvColumnBox.qml`), `ImportPreviewPage.qml`, `ImportDonePage.qml`, which asks about the new transactions' Transfers through `TransferPrompt.qml`. `csv_preview` in `kassensturz-import` gives the column screen the file's first rows as text.
- `src/history.rs` writes the change history as text for the screens (M3.8, D-121): the change `Book::undo` would take back and the one `Book::redo` would make again, with what they touched (`Book::change_summary`), the newest 100 changes, the retention setting (`forever` or a number of days) and how many changes a shorter setting would delete. Each change has an action key (`action_key`, exhaustive over the store's actions) that `ChangeNames.qml` puts into words; a test checks that every key has a name there. `src/history_model.rs` is its QML object, `ChangeHistory`: `undo()` and `redo()` change the book and emit `changed`, like the other screens' objects, so `Main.qml` reads everything again, closes pages for what may be gone (`survivesUndo`) and says what was done in a notice with the way back. The retention choice and Clean up history are in `SettingsPage.qml`, the list in `HistoryPage.qml`.
- Mistakes in what the user typed come back as codes starting with `input.` plus parameters as text; the QML (`FormError.qml`) writes the message (D-034). They belong to the app, not to core or store, so `docs/ERROR_CODES.md` doesn't list them; store errors keep their codes from there.

## The app's shell and its books (M3.1)

- The window (`qml/Main.qml`) opens the book and shows one screen at a time, each in a QML file of its own, chosen from a side menu once the book has an account. A screen is added with its file, a line in `build.rs` and an entry in `Main.qml`, so steps can add screens side by side (D-113).
- `src/books.rs` opens books (D-033, D-113): the book opened last, or at the first start the app's own book in KassenSturz's data folder; a missing book is never replaced by a new one. Problems come back as codes with parameters as text, `store.` codes from the store and the app's own `book.` codes (`book.missing`, `book.sandboxed`, `book.no-app-folder`); the QML (`BookProblemPage.qml`) writes the message and offers what to do next, such as "Open anyway" for a locked book (D-038, D-080).
- `src/session.rs` keeps the open book for the GUI thread; `src/book_session.rs` is its QML object, `BookSession`, which opens and switches books and signals `opened` so every screen reads the book again. Every screen's Rust object reaches the book through `session::with_book` and `session::with_book_mut`. The app closes the book before it ends, which removes the lock file.
- `src/settings.rs` keeps the app's own settings with KConfig, in `kassensturzrc` in the user's settings folder (D-112): the book opened last, and the number format (D-114). The Rust program links KConfig's core library through `cpp/settings.cpp`; `build.rs` finds it next to Qt, or where CMake's `KF6::ConfigCore` says when CMake drives the build.
- `src/platform.rs` asks Qt for the computer's name, the data folder and the file system a book is on (`QStorageInfo`), to warn about network drives (D-038) and refuse files a sandbox's file chooser handed over (Q-071), until `kassensturz-platform` takes this over.
- `src/network_guard.rs` and `cpp/local_only.cpp` give the QML engine a network access manager that refuses every address except local files and Qt resources, so no screen can reach the network, whatever a text contains (D-143). `qml/Plain.qml` is the helper for Kirigami messages that show outside text; `src/plain_text_audit.rs` is the test that every label with changing text is plain text.

## Number format (M3.2)

- `src/format.rs` writes an amount from its exact value (D-065): the `Locale` trait supplies separators, grouping and the text around the digits, and `AmountFormat::format_rounded` rounds only for display when fewer decimal places are shown (D-002), in 128-bit integers.
- `src/number_format.rs` holds the user's choices (`NumberFormat`, kept in `kassensturzrc`, D-114) and `UserLocale`, which applies them on top of Qt's locale data (`QtLocale`). Every screen writes and reads amounts through `number_format::app_locale()`, so the choices reach typing as well as display; `register.rs`'s `AmountWriter` returns each amount as shown and exactly (`Shown`), and QML shows the exact one on hover (`AmountLabel.qml`).
- `src/number_format_model.rs` is the Settings page's QML object, `NumberFormatSettings`: each setting's choice as the word the settings file keeps, examples written the chosen way, and `choose()`, which saves; `Main.qml` reads the screens again when a choice changes.

## Accounts and categories (M3.3)

- `src/accounts.rs` and `src/categories.rs` hold the logic of the two screens, over the public functions of core and store, with no Qt in them, so their tests run on books in memory. They return plain structures (`AccountsView`, `CategoryView`, `BankCheck`) with every amount already as text (`Shown`, D-065) and report refusals as codes with parameters (`errors.rs`, D-034).
- `src/accounts_model.rs` (`AccountList`) and `src/categories_model.rs` (`CategoryTree`) are the QML objects. They reach the open book through `session.rs` and name accounts and categories to QML by their ID as text; every change ends in their `changed` signal, which `Main.qml` answers by reading the other screens and the first-run mock again. `variant.rs` turns structures into the plain values QML takes.
- `Book::balance_on` (store) is the balance of an account at the end of a day by the bank's booking date; the import's balance check (`kassensturz-pipeline`) and "Check against my bank" use the same rule through `AccountPart::bank_date`.
- QML: one file per screen (`AccountsPage`, `NewAccountPage`, `AccountDetailsPage`, `BankCheckPage`, `CategoriesPage`, `CategoryPage`), with `AccountCard`, `Balance` and `AccountTypes` shared.

## First start (M3.4)

- `src/first_start.rs` says where a book stands (`FirstStart`: whether it has an account, whether the currency must still be asked, the currencies to offer) and completes the first start: the chosen currency and the default categories, written as a tree in one user action (D-116). The names come from QML (`DefaultCategories.qml`), where KI18n translates them; Rust checks the list and writes it. `src/first_start_model.rs` is its QML object, `FirstStart`.
- `accounts::correct_starting_balance` carries out the offer of "Check against my bank" (D-111): `BankCheck::correction` says what it would do, and only the user's click does it, as one change (`Action::CorrectStartingBalance`): the edited or added transaction plus the stated balance.
- **The stated balance (M3.4a, D-117):** `Book::stated_balance` and `Book::set_stated_balance` keep what the user said the bank showed and the day (layout 14, two columns of `accounts`). `accounts::add_account` notes it when a balance was typed, `correct_starting_balance` when the user confirms. `accounts::details` compares it with `Book::balance_on` for that day (`Statement`), and `AccountDetailsPage` shows the result; when the account no longer holds it, the page sends the user to `BankCheckPage` with the stated balance and day filled in (`initialBank`, `initialDate`), which compares at once and offers the correction.
- QML: `WelcomePage` (currency question and start), `NewAccountPage` with `firstRun` (the first account), the mock's `TransactionPage` for the optional first transaction. `Main.qml` shows the welcome page until the book has an account and reads every screen again after a change (`bookChanged`).

## Dependency rules

- `kassensturz-core` depends on **no other workspace crate**.
- `kassensturz-store`, `kassensturz-import`, `kassensturz-export`, `kassensturz-bank`, `kassensturz-platform`, `kassensturz-charts`, `kassensturz-ai`, `kassensturz-plugin-host` depend on `kassensturz-core`. `kassensturz-ai` also depends on `kassensturz-platform` for the provider's key (D-184), and on no other KassenSturz crate.
- `kassensturz-ai-chat` joins `kassensturz-ai` and `kassensturz-ai-tools` (and the store for the `Book` they read): `kassensturz-ai` can't open a book (D-182, T-24) and `kassensturz-ai-tools` has no network code (D-175), so the chat that needs both is a crate of its own, and only the desktop app depends on it; `kassensturz-mcp` never does (D-190).
- `kassensturz-bank` also depends on `kassensturz-import`, for the `Statement` it converts fetched data into and the checks every statement gets (D-145); it knows no book. Its tests alone depend on `kassensturz-pipeline` and `kassensturz-store`, to feed the fake bank's statements through the real import (AGENTS.md §9.4).
- `kassensturz-store`, `kassensturz-import` and `kassensturz-export` don't depend on each other: a file format knows no database, and the book knows no file format (D-091, D-099). `kassensturz-pipeline` depends on core, import, export and store and joins them (D-092, D-099).
- Only `kassensturz-store` touches the book's database; every other crate calls its functions (D-072). Reading another program's files, such as KMyMoney's SQLite format in `kassensturz-import`, isn't affected.
- Only `kassensturz-bank` uses `kassensturz-aqbanking-sys`; no other crate calls AqBanking's C code (D-060). `kassensturz-bank` also depends on `kassensturz-platform` for the keychain its saved PINs live in (`KeychainPinStore`, D-057). The tests of both crates load `kassensturz-aqbanking-stub`, a `cdylib` that is never shipped, in place of the real libraries (feature `stub` of the `-sys` crate builds it; the `-sys` crate turns the feature on for its own tests through a dependency on itself).
- Front ends (`kassensturz-cli`, `kassensturz-ui-bridge`, `kassensturz-mcp`) depend on core, store and plugin host, and on import, export and pipeline to import and export files; the desktop app also on `kassensturz-bank` and `kassensturz-platform` for bank connections (D-151). **Core never knows about a UI.**
- OS-specific behavior lives only in `kassensturz-platform` behind traits. Since M4.1 that is the `Keychain` trait: `SystemKeychain` reaches the user's keychain through the `keyring` crate (the Secret Service on Linux, which KWallet and GNOME Keyring answer), `MemoryKeychain` is the fake for tests, and a `Secret` never shows its value and wipes itself (D-147). `kassensturz-platform` depends only on `kassensturz-core`; no other crate talks to a keychain (AGENTS.md §3.1 rule 7).
- AI code lives only in `kassensturz-ai`, `kassensturz-ai-chat`, `kassensturz-ai-tools` and `kassensturz-mcp`; `kassensturz-ai-tools` reads the book through `kassensturz-store` and has no connection crate, `kassensturz-ai` alone holds the HTTP client (D-175, T-13), and `kassensturz-mcp` carries only `rmcp`'s stdio transport, with tests that prove it opens no socket (D-175). Front ends use them only behind one build feature (`ai`, on by default), so KassenSturz can be built without any AI code (D-039). `kassensturz-core` never depends on AI code.
- Built-in importers and exporters implement the native Rust interface that the plugin API mirrors (D-069).

## Plugin model

- The WASM plugin host comes after 1.0 (D-071). Until then, built-in importers and exporters implement native Rust traits that the plugin API will mirror (D-069).
- Extension points: Importer, Exporter, Report, Automation.
- Versioned API. Manifest declares name, version, target API version, permissions.
- Narrow, permission-checked data access. No raw SQL access.
- WASM only, for sandboxing and cross-platform portability. Out-of-process (JSON-RPC) plugins are not part of v1: they can't be sandboxed, so the permission model couldn't be enforced for them (D-007).
- Users add a downloaded plugin file, in KassenSturz's plugin package format (defined with the plugin host), in the **Plugins** tab, which shows the permissions it requests. No plugin store in v1: a store run by the project would be a hosted service (AGENTS.md §3.3).
- The Importer part of the plugin interface is defined during M1–M2 as a native Rust trait: built-in importers implement it directly, and the WASM plugin API mirrors it once it exists (D-069, D-071).

## Transactions and Parts (splits)

- A transaction can be broken down into multiple categorized **Parts** (UI term for `Split`, see `docs/GLOSSARY.md`) at any time, not only at import — see D-017.
- Editing Parts auto-calculates one remaining Part's amount as "total minus what's already entered." Saving is rejected unless all Parts sum exactly to the transaction's original amount — enforced in `kassensturz-core`, not just in the UI.
- Manual entry only in this decision; deriving Parts from a scanned receipt (OCR) is taken up separately in D-018.
- A Part in another currency keeps its original amount and currency plus its value in the transaction's currency (the rate used, stored as a fixed-point decimal, D-051), so every transaction adds up to zero in its own currency (D-043). Every Part is in its account's currency; when an amount was converted with a rate from the price table, the Part keeps a copy of that rate (D-083).
- A Part can have no category yet: an import adds the bank's entry plus such a Part, which a Rule or the user then categorizes (D-083).
- What a bank or file delivered is kept with the Part booked to the account the statement is for, so a Transfer matched from two statements keeps both (D-083). That Part's account and amount never change; the other Parts, the payee and the date can.
- A transaction is changed by replacing it as a whole, with the same ID (`Book::update_transaction`), and checked like a new one. Changing or removing it can be undone like every change (D-032, D-086).

## Command-line tool

- `kassensturz-cli` is a front end like the app, so it uses only the public functions of `kassensturz-core`, `kassensturz-store`, `kassensturz-import` and `kassensturz-pipeline` (D-072, D-085). Until the first real format comes (M2.3), its `import` command reads `kstest`, a made-up format for tests that the app never offers (D-092). It is for developers and testers: it isn't installed by the Flatpak or CMake and isn't translated (Q-040).
- It was the first front end to open book files, so it supplies the computer's name and the backup folder (`Computer`, D-080) from options or a best guess, until `kassensturz-platform` takes that over.
- Amounts go in and out as plain text (`-12.50`) with the currency's decimal places, never rounded; errors are written as their code and parameters (D-084).
- Run it with `tools/sdk.sh cargo run --bin kassensturz-cli -- help`.

## Multiple accounts and Transfers

- Multiple accounts live side by side in one book (D-003); the UI shows an overview across all of them, not one account at a time — see M3 in `docs/ROADMAP.md`.
- When import sees a debit in one of the user's accounts and a matching credit in another account **already in the same book**, it proposes merging them into one double-entry **Transfer** (both splits are real asset/liability accounts, no income/expense category) instead of recording them as two unrelated transactions. See D-021.
- Matching: amount (same currency) or a plausible exchange rate for cross-currency transfers (D-004) + date-proximity + both accounts already present in the book. External IBANs are never candidates.
- Date window: up to 3 business days between the two sides; same currency only for now (D-030; cross-currency tolerances are Q-020).
- Always a suggestion the user confirms, every time, in v1; a "trust this pair of accounts" option may come later (D-030).
- The heuristic is `kassensturz_core::find_transfers`; `Book::transfer_suggestions` runs it on the transactions whose other part has no category yet, and `Book::join_transfer` turns a confirmed pair into one Transfer: the outgoing transaction gets the incoming account's part, with what its bank delivered and, as the part's own, the date and payee that account showed, and the incoming transaction goes (D-087, D-108). So neither account's register changes: each keeps the day its own bank booked the money, while the Transfer has one date, the outgoing side's.
- Reports exclude confirmed Transfers from income/expense totals — a direct consequence of the existing double-entry model (§5), not a separate reporting rule.

## Importers

- Every format implements `kassensturz_import::Importer` (D-069, D-091): `info` (a stable ID such as `camt053`, what reading gives, the usual extensions), `recognize` (yes, maybe or no from the first 4096 bytes) and `read` (the file's bytes into `Imported` data). An importer only reads; it never sees a book. Settings a format needs, such as CSV columns, belong to the importer's own value. `Csv` is made from the user's `CsvSettings` (encoding, separator, decimal mark, date order, which column holds what) and the account's currency, and guesses nothing (D-095); the settings have a text form, `key = value` per line, for keeping them.
- `Imported` holds bank statements (`Statement`: the account as the file names it, the currency with its decimal places, opening and closing balance, entries). A whole book another program kept is the second variant, `ImportedBook`: accounts and categories named by the file's own keys, transactions whose parts needn't add up, the rates, the currencies neither of KassenSturz's tables lists with what the file's rates suggest replaced them (`unlisted`, D-106), and how many of each kind of data was left out (`SkippedData`, D-029). `Kmy` reads KMyMoney's `.kmy` files into it (D-101), and `KmySqlite` KMyMoney's SQLite files, through the same mapping (D-103). Both `Imported` and `ImportKind` are `#[non_exhaustive]`.
- An `Entry` is booked or pending, with the bank's ID, booking date (always there), value date, amount as it changes the account, the other party's name and IBAN and the remittance information, all text as delivered (D-067).
- Files are untrusted (AGENTS.md §8): front ends call `import` or `import_file`, which enforce `Limits` (size, nesting, entries, text length) and check what the importer returned, e.g. that every amount is in its statement's currency. Text is passed on only as data.
- Amounts are read exactly by `parse_amount` (decimal point or comma, no rounding, AGENTS.md §3.1 rule 1).
- Golden-file tests: `crates/kassensturz-import/tests/golden/<importer id>/` holds synthetic files, each with a `.expected` file of what importing it gives and, for an importer that needs settings (CSV), a `.settings` file it reads the file with, written by `tests/import/harness.rs`; `KASSENSTURZ_BLESS=1 cargo test -p kassensturz-import --test import` writes them. A new importer adds one test to `tests/import/main.rs`.

## Import pipeline

- `kassensturz-pipeline` puts statements into one account of the book (D-092). `import_statements` is one user action, `import_statement` (layout 10), which undo takes back as a whole (D-086). `preview_import` runs the very same steps inside `Book::dry_run` and takes them back, so the preview shows exactly what the import would do, Rules and Transfers included. Every front end calls these two, so the order of the steps lives in one place.
- The account must be one of the user's open accounts, and each statement in its currency with the decimal places the book stores for it (D-027); otherwise nothing is imported (`import.account-currency-differs`, `import.decimal-places-differ`). A statement in a withdrawn currency, such as the Mark, goes into an account in the currency that replaced it: its entries are converted as the bank converted the account's balance, each new transaction keeps the entry's amount in the old currency, and the bank's closing balance is converted for the balance check; into an account in any other currency it is refused (`import.replaced-currency-differs`, D-105).
- Steps run in this order: only booked entries, the duplicate check, then Transfer matching, then Rules (D-030):
  - Entries the bank hasn't booked are left out and counted.
  - Duplicates: an entry whose bank ID the account already holds, or that an earlier entry of the same import has, is skipped and counted in the import summary (Q-039, D-083). Other accounts' IDs don't count, and an empty ID is no ID.
  - Uncertain cases are left out until the user chooses to import them (`Choices`): an entry that has the same amount as a part the account already has, at most 3 business days apart by the day the bank booked it, unless both have bank IDs and they differ (D-092). Transactions typed in by hand count, so a purchase entered before the statement came is caught. Entries of one import are never compared with each other: two coffees of the same price on one day are two coffees.
  - Each other entry becomes a transaction: the account's part, with everything the bank delivered, plus one part without a category (D-083). The payee is the other party's name, which the user can change.
  - The Transfers to suggest that involve a new transaction (`Book::transfer_suggestions`, D-087), for the user to confirm.
  - The Rules, on the new transactions only (`Book::run_rules_on`, D-088). A side of a suggested Transfer waits for the user's decision.
- The balance check: for each statement with a closing balance, KassenSturz's balance of the account at the end of that day, everything booked to it up to then by the day the bank booked it where it says so, against the bank's (D-029). A difference is shown, never corrected automatically.
- A whole book (`ImportedBook`) only ever goes into a new, empty book: `fill_book_from` gives everything new IDs, makes names unique where the book needs them to be, adds a part without a category to a transaction whose parts don't add up, and fills the book through `fill_book`, the same way as a complete export, so every check of the store applies and the change history stays empty (D-100, D-101). A currency neither table lists comes in only with the successor, rate and day the user typed in (`Replacement`, D-106), never the file's suggestion by itself. Its report says what it changed, what was left out, and which Transfers to suggest.
- Both booking date and value date are stored, with the Part the bank delivered; the transaction's booking date is the one shown, and the user can change it (D-083).
- What a bank or file delivers (other party name and IBAN, remittance information, bank transaction ID) is stored unchanged next to the payee and category the user can edit, so Rules can be re-run and duplicates recognized later (D-067).
- Only booked transactions are imported in v1; pending ones (not yet booked by the bank) are skipped (D-030).
- Bank connections through AqBanking only read balances and booked transactions; KassenSturz never sends payments (D-053). AqBanking comes from the system in distro packages and is bundled in the Flatpak, Windows and macOS builds; KassenSturz detects it at runtime and works without it. Bank setup, PIN and TAN entry use KassenSturz's own Kirigami screens; Gwenhywfar's dialogs are left for later (D-151, Q-089). Logins: PIN/TAN or a bank chip card; no key files, so no EBICS (D-059). The code lives in `kassensturz-bank`, on top of the raw `kassensturz-aqbanking-sys` declarations (D-060). The PIN is asked each time unless the user chooses to remember it until KassenSturz closes (memory only) or to save it in the system keychain through `kassensturz-platform` (D-057). Tests run against a fake bank backend (D-055). Live FinTS connections need KassenSturz's own FinTS product registration, passed to AqBanking as `fintsRegistrationKey`; never another program's number (D-058). Builds carry none: with `KASSENSTURZ_FINTS_ASK=1` the tester types it when a bank is first contacted, and `kassensturz-ui-bridge` gives it to the open session for that run only (D-260).
- The KMyMoney importer is built clean-room, from sample files and public documentation only (D-044). It skips data KassenSturz can't hold yet (investments, schedules, loans, …) and reports what it skipped (D-029).
- A KMyMoney payee that has a default category becomes a Rule: the importer returns it in `ImportedBook::rules` (`BookRule`: the file's matching texts as `conditions`, the payee's own name as `name_conditions`, the file's own account key), and `fill_book_from_with` takes a `RuleScope` that decides what the Rule matches (the file's texts or the name, or only the file's texts and no Rule without any). It gives it an ID, checks each pattern with `Rule::check` (the `regex` crate doesn't take everything a Qt expression does), books to a category or, for one of the user's accounts, a Transfer, and reports what it couldn't use (D-160).

## Multi-user support (post-1.0)

- New concept **Member** (a person using KassenSturz), kept distinct from financial **Account** — see `docs/GLOSSARY.md`. See D-022.
- Each Account has an owner Member and can be explicitly shared with other Members; private to its creator by default.
- Visibility scoping (which Accounts a Member can see/use) is enforced **once**, in `kassensturz-core`/`kassensturz-store` — not reimplemented per feature. Rules, Parts, Transfers and receipt matching all inherit it automatically: a shared Account's imported bills can be completed from either Member's phone (D-019) because that Account is in both of their visible sets.
- Topology: a **shared host with thin clients**. One household-owned device (desktop or home server/NAS) runs the authoritative `kassensturz-store`; other desktops and phones connect over the **local network** via `kassensturz-sync` as thin clients, rather than each holding their own full copy.
- Not a project-run hosted service (§3.3 non-goal) — the host is infrastructure the household itself owns and runs.
- Requires network access for thin clients to reach the host; must stay opt-in and off by default (hard rule 3.1.4) — a single-user, single-device install has zero network exposure unless multi-user is deliberately turned on.
- SQLite's weak concurrent-write story may force one of D-016's planned non-SQLite backends for the host role; not decided (Q-021). Transport/protocol (Q-022) and Member authentication strength (Q-023, a visibility feature, not a security boundary) are also open.

## Rules (auto-categorization)

- Modeled on email-client filters (Thunderbird/Outlook), not KMyMoney's name-only matching. See D-014.
- A Rule = conditions (field + operator + value, matched ALL or ANY) + actions (v1: set category, set payee, make it a Transfer — D-031).
- Fields, extensible as KassenSturz learns more about a transaction: Other party name, Other party IBAN, Purpose (remittance information), Payee, Amount (exact, a range, money in or out), Booking date, Currency and the user's account (D-088). A new text field is one more `TextField` entry.
- Regex is an explicit opt-in per condition, backed by Rust's `regex` crate for guaranteed linear-time (ReDoS-safe) matching. See D-015.
- Rules form a tree. A sub-Rule is only evaluated if its parent matched; a matching sub-Rule's action overrides the parent's. Between top-level Rules, the first match in the user's order wins (D-031).
- Applied automatically to newly imported transactions, after the duplicate check and Transfer matching (D-030); a manual "run Rules" action applies them to existing transactions that have no category yet. A Rule books a transaction once; when the user changes a Rule, they can have it book again what it booked (D-088). It never changes a category set by hand or a transaction broken into Parts (D-031), and it can be undone through the change history (D-032).
- Rule suggestion: when the user has given transactions from the same payee the same category by hand several times, KassenSturz offers to create a Rule. Plain code that works with AI off; the user confirms (D-071).
- `kassensturz_core::RuleSet` checks a tree of Rules, compiles its patterns once and evaluates a transaction's facts (`RuleFacts`). `kassensturz-store` keeps the tree in the book (layout 9) and runs it: `Book::preview_rules` changes nothing, `Book::run_rules` is one user action. A run books only a transaction with two parts, one for the user's account and one without a category yet, and marks the part it booked in `split_rules`; `Book::update_rule_and_rebook` changes a Rule and books again what it and its sub-Rules booked, in the same user action (`Book::preview_rebook` shows that first). Changing a transaction by hand drops the mark, so manual edits win (D-031, D-088).
- Deterministic and code-driven — entirely separate from the AI model below (§8 of AGENTS.md does not apply to Rules).

## Receipt capture (post-1.0)

- One shared pipeline in `kassensturz-receipts` behind two entry points: a future KassenSturz Android companion app (camera capture) and a desktop-only function that imports an existing scan/photo file — see D-018.
- Pipeline: OCR extraction → deterministic matching heuristic (amount + date-proximity + fuzzy payee name) against already-imported transactions → proposes a Parts breakdown (D-017) from the receipt's line items.
- The match and the proposed Parts are always a suggestion; nothing is written to a transaction without user confirmation.
- Must work fully with AI off (D-013). An optional AI-assisted extraction path through `kassensturz-ai` may help on messy receipts once AI is on, but is never required.
- Phone-to-desktop transfer is not a project-run hosted service (§3.3 non-goal); see Q-015 for the local-network-pairing vs. file-drop choice.
- The Android app is a **separate native app** (D-019), not the Qt 6/Kirigami stack via Qt for Android. It reuses `kassensturz-core`/`kassensturz-receipts` through `kassensturz-mobile-bridge` (a Rust↔Kotlin FFI binding, e.g. UniFFI — not pinned yet) rather than reimplementing money-handling or matching logic natively. Exact UI framework and FFI approach are open (Q-018); adding Android to the Portability principle's platform list (AGENTS.md §2) still needs its own maintainer sign-off when this is actually scheduled.

## AI model

- `kassensturz-ai` defines a provider trait. v1 adapter: OpenAI-compatible HTTP only (Ollama, llama.cpp server, LM Studio, vLLM, and cloud services offering the same API); dedicated cloud adapters may follow later (D-035). Since M5.2: `AiClient` reads the AI settings from the settings file at every call and checks the switch, the provider's address (plain `http://` only on loopback), that the request was prepared for that provider, the consent for another computer and the key, in that order, before it builds the HTTP client (`ureq` with `rustls`, the system's certificate store, no proxy, no redirects, size and time limits; D-182, D-183). A request is prepared first; its preview is the exact body sent, and the user can redact phrases from it. `ProviderKeys` keeps the key as for a PIN, filed in the keychain under the provider's server (D-184). Errors are `ai.` codes. Tests use a fake provider on `127.0.0.1` in `tests/fake/`, never a real one. The four providers KassenSturz is tried with (OpenAI, Claude and Gemini through their OpenAI-compatible endpoints, LM Studio) are tested as written-down answers in `tests/dialect/fixtures/`, plus the rules each request is checked against, in the adapter and in the chat; they are not recordings, M5.B checks the real providers (D-206 to D-209). The reader gives a call without a usable ID its own, reads empty arguments as `{}` and a refusal as text, and a message that only calls functions has no content (D-207). `ScriptedProvider` is a provider played by a function in the app, with no connection, for tests and the fake model (D-193).
- `kassensturz-ai-chat` (M5.4) holds the conversation: `ChatSession::ask` sends KassenSturz's English instructions (the build and that it is a pre-release, D-174, D-191) with the read functions, runs the functions the model calls on the book and hands back their results until the model answers, at most 8 requests per question; a call for a function not offered is never run, and a provider that refuses functions (HTTP 400 before any call worked) gets the overview instead (D-190). The answer comes with the numbers no function produced (D-188). The tool-call log holds the question, the exact body of each request and each call with its result, in memory only (D-192). `Hooks` let the front end show and redact each request before it goes, and stop a question; replies are read whole, without streaming, and a reply that comes after a stop is thrown away (D-193). The fake model (`demo_provider`, offered when the app is started with `KASSENSTURZ_FAKE_AI=1` or `=overview`) answers from the real functions without any AI (D-193). Its `Feature` (M5.9, D-222) turns a button of the chat or the register into a fixed question, built from dates and an optional account ID only, which goes through the same `ask`; there is no second path to the model.
- Built-in AI features, all on demand and used through a chat panel in the app (D-047): category suggestions, answers to questions and summaries the user asks for (every figure computed by code: the AI calls KassenSturz's functions, or gets a small precomputed overview if the model can't call functions, D-052), and changes the AI prepares, such as new categories, Rules or charts. Proposals that turn recurring patterns into Rules or saved reports come with AI memory, after 1.0 (D-071).
- A consent layer decides what data may leave the machine, per provider, with preview and redaction. A model on another computer, even one at home, counts as leaving the machine (D-035).
- Changes proposed by AI are represented as reviewable change sets and applied only after user confirmation. Writes requested through `kassensturz-mcp` are confirmed in the KassenSturz window (D-035). Since M5.5: `kassensturz-ai-tools`'s `src/changes.rs` turns a model's call of `propose_changes` into a `ChangeSet` (`propose`, checks of D-199) whose `ProposedChange`s are the preview, and `ChangeSet::apply(book, Confirmed)` runs the store's operations as one `Action::ApplyAiChanges` (layout 18, D-198), all or nothing, after checking that no transaction in it changed (D-200). The chat offers the function and returns the sets in `Answer::changes` (D-201); the request-file transport of M5.10 hands over the same JSON.
- The chat panel and the change-set review (M5.8, D-210 to D-213) are in `kassensturz-ui-bridge`: `src/ai_chat.rs` (no Qt) runs a question on a thread of its own over `Book::open_to_read`, shows each request to another computer or the fake model to the user through the `Screen` trait and `Command`s, and keeps the change sets that wait; `ai_chat_model.rs` is the `AiChat` object (properties `available`, `busy`; signals `logged`, `reviewing`, `finished`, `changed`); `qml/AiChatPanel.qml` is the right-hand sidebar (the window's `contextDrawer`), `AiRequestReview.qml` the look at a request, `AiChangeReviewPage.qml` the review page whose confirm button reaches `ai_chat::confirm_in`, the only place that makes a `Confirmed`. The key for one question comes from `ai_settings::with_keys`, the holder the settings page uses.
- Before confirming, the user may correct a waiting set on the review page (M6b.8, D-293, D-297): `kassensturz-ai-tools`' `changes/edits.rs` keeps the model's call and the user's version of single items by their slot, and checks the edited call with the same `build` as `propose`; the bridge's `AiChat.editChange`, `leaveOutChange`, `backToAi` and `changeChoices` reach it, and `AiChangeCorrection.qml` is the row under each change.
- `kassensturz-mcp` serves the core to the user's own AI tools outside KassenSturz (e.g. Claude Desktop, LM Studio), over stdio only: the outside tool starts it, and no network port is opened (D-050). Read-only by default; write tools can be switched on separately, and every write is confirmed in the KassenSturz window (D-035). The chat panel doesn't use it.
- `kassensturz-mcp` (M5.6) offers the same read functions as the chat (`kassensturz-ai-tools`), served by `rmcp` on a one-thread Tokio runtime without an I/O driver (D-194). It reads the book the app opened last, or the one given with `--book` (D-196), beside the running app: `Book::open_to_read` opens it read-only without a lock, each answer is one short read transaction (`Book::reading`), and the app's writes wait for it (D-195). It tells the AI tool which pre-release build it is (D-197).
- MCP writes (M5.10): with the toggle `[AI] McpWriteTools` on (D-219), `kassensturz-mcp` offers `propose_changes` and `check_proposed_changes` (`src/writes.rs`, D-217). It checks a call with `propose`, then hands it to the running app as a file in the user-only request folder (`kassensturz_ai_tools::requests`, D-216) and waits for the answer file. The app's `ai_requests.rs` takes requests through the `Inbox` trait, checks them again on its own book and puts the sets beside the chat's in `ai_chat::Sets`; the review page and `confirm_in` apply them (D-218). Only `RequestFolder` knows about files, so a socket later replaces only it.
- AI settings (on or off, provider address and model, consent record) are kept in the app's config file on this computer, never in the book (D-168); the provider's key is only in the keychain (D-169). Threats and the rules for AI code are in `docs/THREAT_MODEL.md` (T-21 to T-35).
- What the AI may do (D-239, D-252): `kassensturz-core`'s `ai_switch.rs` holds `Permission` (the cells of the grid: four Read cells and twelve kinds of change, D-253 to D-258 and, since M6a.9, the Charts › Add cell `AllowNewViews` of `new_views`, D-282; `changes/views.rs`), `Row`, `Field` (the lockable fields of a transaction) and `Permissions`, read from the `[AI]` group of the settings file (`AllowNewRules`, `AllowReadRules`, `LockAmount` and so on; none while AI is off, an odd value is off or locked, everything off by default except the locks of amount, date and payee). A change or a deletion gives the reading of its row. `call_allowed`, `overview_allowed` and `readable_functions` apply the Read cells. `kassensturz-ai-tools` enforces them: `propose(book, args, permissions)` refuses a list that is not allowed, `propose_spec` builds the function a model is offered with only the allowed lists (none when nothing is allowed), `ChangeSet::check_allowed` runs again at the confirm. The chat session and `kassensturz-mcp` read the settings for each request, so the same boxes govern both; the sidebar hides the buttons of a feature whose kind is off. The Transactions/Change cell covers two lists, `categorize` (needs the Category field unlocked) and `edit_transactions` (D-257, `changes/transactions.rs`: date, payee, note, amount and account, each only while its field is not locked; amount and account only on a plain transaction no bank or file delivered); The Transactions/Add cell offers `new_transactions` (D-258, `changes/cash.rs`: a payment in cash in a cash account; needs account, day and amount unlocked) and Transactions/Delete offers `delete_transactions` (a by-hand entry of a cash account); the grid shows a danger warning while either or Change is on (D-259). `propose_spec` removes the properties of locked fields from what a model is offered, and `check_allowed` re-checks them at the confirm.
- Developer mode and issue drafts (M5.13, D-227, D-228): `kassensturz-core`'s `debug_log.rs` (feature `debug-log`) writes the debug log, like `ai_switch.rs` the one small file the core touches itself: only `Event`s, details from the fixed list in `vocabulary.rs` (function, tool and screen names) and checked error codes (`error::is_error_code`), never free text, and only while the app was started with `KASSENSTURZ_DEBUG_LOG=1`. The chat (`log.rs`'s `LogEntry::debug_event`), the bridge (`developer_mode.rs`, the `note!` macro, and the banner in `Main.qml`) and `kassensturz-mcp` record into it; `kassensturz-ai-tools`'s `debug_log.rs` (`read_debug_log`) returns it to a model only while AI is on too. `kassensturz-ai-tools`'s `issue.rs` (`draft_issue`) builds an issue from a fixed template after scanning the model's text against the book; the chat card opens the prefilled GitHub page in the user's browser or copies the text, with no network code in KassenSturz.
- A global AI-off switch is a kill switch: `kassensturz-mcp` refuses to start while AI is off, and `kassensturz-ai` runs no provider code. The UI layer hides (not disables) every AI-related element in that state, except one "AI features" toggle in Settings. See AGENTS.md §8, D-013.

## AI memory (post-1.0)

- Moved to after 1.0 (D-071). Until then, the chat learns about the book through KassenSturz's functions and the small overview (D-052), computed fresh each time.
- `kassensturz-ai` keeps its own local "memory" (see D-023), analogous to this repo's own AGENTS.md/agent-memory setup — but for interactions with the user, not with code.
- Two parts: a maintained **context document** about this book's own setup, and a **pattern memory** of recurring interactions (e.g. "this payee is often categorized as X"). Both are rows in `kassensturz-store` (D-016), not separate files, so they stay inside the one-file book.
- Purpose: let AI **propose promoting a repeated pattern into a Rule (D-014) or a saved report** — never a parallel source of authority. Never caches balances or totals; those are always recomputed by code.
- Passive/on-demand only: consulted while the user is actively using AI, no unprompted notifications in v1 (Q-024).
- Follows every existing AI rule: off entirely when the AI off-switch is on (D-013); any of it sent to a provider goes through the same consent/preview/redaction flow as other context (§8); treated as data, never instructions, like any other untrusted text.
- User can view, edit or delete entries, individually or all at once, any time.
- Once Members exist (D-022), scoped the same way Account visibility already is — inherited, not reimplemented.
- Whether `kassensturz-mcp` exposes any of this to external AI tools is open (Q-025); retention/frequency tuning is open (Q-026).

## User-facing text

- `kassensturz-core` never produces user-facing text: it returns structured error codes (with parameters), and the UI owns every string (D-034). Every error of core and store turns into an `ErrorReport`: a stable code, typed parameters and its cause. `docs/ERROR_CODES.md` lists every code and suggests an English message for it (D-084).
- Translations use KDE's KI18n (gettext). v1 ships in English (source language) and German.
- Numbers are shown in the user's regional format by default (100,00 € in Germany, $100.00 in the US); the user can change the format and the number of decimal places shown. Display settings live in the app's settings, not in the book, and never change stored amounts or calculations (D-002).
- Amounts reach QML only as text: Rust formats them from the exact value, with separators and currency symbol from Qt's locale data, and parses what the user types. Sorting and totals happen in Rust models; floating point appears only as chart drawing coordinates (D-065). How the pieces are taken from Qt: D-075.
- QML gets its translations through KI18n's `KI18nContext`, created in QML, so the Rust program doesn't link KI18n (D-074). The only KDE Frameworks library it links is KConfig's core library, for the app's settings (D-112, D-113).
- Plain-language terms come from `docs/GLOSSARY.md`; for example, the other side of a transaction is shown as "From"/"To" and is called "Other party" in the Rule editor.

## Data and portability

- One SQLite file per book in v1, managed by the app; "Open another book…" exists for power users. SQLite runs with the rollback journal, not WAL, so no lasting side files sit next to the book (D-033).
- Book files use the extension `.ksz` and carry the SQLite application ID `KSZB`, so KassenSturz recognizes its own books whatever they're called (D-037). The store checks it before SQLite opens a file, so another program's SQLite file is never changed (D-080).
- A book is open in only one place at a time: a lock file next to it (computer name, time) travels with sync tools, so a second computer shows a clear message instead of editing its own copy. SQLite's locks only work within one computer (D-038). Opening the book anyway after that warning takes over the lock only if it is still the one the user was warned about (D-080). A book on a network drive opens with a clear warning (D-038). Sharing a book between people comes after 1.0 (D-022).
- Versioned migrations, run in one transaction, with an automatic backup before every migration, kept in KassenSturz's own data folder (the last 10 of each book, D-033, D-080). Before 0.1, development migrations are merged into one starting layout (D-045).
- Every change is recorded in a change history inside the book: undo/redo and an audit trail (D-032). It stores the before and after values of every row a user action touched; undo works after a restart, and the user sets how long the history is kept: 30 days by default, or forever; 0 stores none, though undo still works while the book is open. "Erase permanently" actions (wiping AI memory, Clean up history) also remove data from the history (D-066).
- `kassensturz-store` records the history itself, with temporary triggers on its own connection to the book, and refuses a change outside a user action, so nothing escapes it. Each public function that changes a book is one user action; a front end groups several calls into one with `Book::as_one_action`. Undo and redo check that the book still holds what the history says and that the result keeps every reference and rule of the book; otherwise they change nothing (D-086). `Book::change_summary` says how many transactions a change added, changed or removed, in which accounts and on which dates, and a change keeps the name of the file it read (`Book::note_file`, without the folder), so a front end can say which change undo or redo takes back; an action that changes nothing, such as an import of entries the book already has, leaves no entry, and the front end says so (D-109).
- Everything in a book is identified by a UUIDv7, not a running number (D-067).
- Each book stores the decimal places of every currency it uses, taken from KassenSturz's own ISO 4217 table when the currency is first used and fixed from then on (D-027, D-062). The table is a data file in `kassensturz-core`, written by `tools/update-currency-table.py` from the codes Debian's iso-codes lists, with the decimal places kept in the table itself (D-062, D-077). A withdrawn currency, such as the Deutsche Mark, isn't in it, and no account can be in one: it is in a second table, `withdrawn.txt`, with its decimal places, the currency that replaced it, the fixed rate and the day, and the update tool moves a code there when it leaves iso-codes' list (`CurrencyCode::withdrawn`, D-104). The importers convert its amounts into the successor, and each converted part keeps its amount in the withdrawn currency with the fixed rate as its original amount (`OriginalAmount`, D-077). Converting a whole book, each account's balance is converted once (`Changeover`), as a bank converted it, so an account the old book emptied is empty in the new one (D-104). A currency replaced before the tables begin, such as the old Romanian leu, is in neither: the user says at import what replaced it, and it is converted the same way (D-106).
- Exchange rates live in the book's dated price table, one per pair of currencies, direction and day, entered by hand in v1 (D-028). A conversion uses the newest rate on or before its date, multiplies by it or divides by it for the other direction, computes exactly in 128 bits and rounds once with the book's rounding mode (D-051, D-079).
- The rounding mode of a book's calculations is stored in the book, so every computer calculates the same way; changing it affects only later calculations (D-027, D-078).
- Export: CSV plus a complete export of the book in an open format (D-029): one JSON file, described in `docs/EXPORT_FORMAT.md` (D-100). It is the stable way to move data.
- The book's layout is documented in `docs/BOOK_FORMAT.md` so other programs can read books. It can change in any version, and writing into a book from outside isn't supported (D-046).
- Paths and keychain access go through `kassensturz-platform`, so Plasma, GNOME, Windows and macOS conventions are handled in one place. Data and config folders are named after the app ID `io.github.vondor.KassenSturz` (D-049). The store doesn't look these up itself: a front end passes it the computer's name and the backup folder when it opens a book (`Computer`, D-080).
- All database code for the book lives in `kassensturz-store`; no other crate touches the book's database directly. SQLite is the only database until 1.0. When another one (PostgreSQL, MySQL/MariaDB, …) is scheduled after 1.0, a storage trait is extracted from the existing code, without changing `kassensturz-core`. See D-016, D-072, Q-012.
