Status values: **Decided** (set by the maintainer) · **Proposed** (agent default, awaiting confirmation) · **Open**.

| D-013 | Decided | **AI has a real off switch.** When AI is turned off: all AI-related UI is hidden (not disabled), no AI code path runs, and no AI-related network connection or local port opens — `kassensturz-mcp` refuses to start (it never opens a network port anyway, D-050). | D-014 | Decided | **Transactions can be auto-categorized by user-defined Rules**, modeled on email-client filters (Thunderbird/Outlook) rather than KMyMoney's name-only matching. A Rule has one or more **conditions** (field + operator + value, matched ALL or ANY) and one or more **actions** (v1 set: D-031). Matchable fields are not limited to payee name — at minimum: Other party name, Other party IBAN (shown to users as "From"/"To", D-034), Amount (equals/range/sign), Remittance information (purpose text), Date, Currency — kept in an extensible field registry, not hardcoded. A condition's value is plain text (contains/equals/starts-with/ends-with, case-insensitive by default) or, as an explicit opt-in, a **regular expression**. Rules form a **tree**: a Rule can have **sub-Rules**, and gated-refinement is the chosen semantics — a sub-Rule is only evaluated if its parent already matched, and if a sub-Rule also matches, its action overrides/refines the parent's; if no sub-Rule matches, the parent's own action still applies. This is fully deterministic, code-driven logic, not AI (§8) — it lives in `kassensturz-core`, independent of any AI feature. |
| D-015 | Decided | **Regex matching uses Rust's `regex` crate**, not a backtracking engine. It guarantees linear-time matching with no catastrophic backtracking (ReDoS-safe), at the cost of no backreferences/lookaround — an intentional trade-off so a casual user's pasted-in pattern can never hang the app. Dual MIT/Apache-2.0 licensed, maintained by the rust-lang project; compatible with GPL-3.0-or-later. See `docs/THIRD_PARTY.md`. |
| D-016 | Decided | **Storage sits behind a backend-agnostic trait from day one** (refined by D-072: until a second database is scheduled, all storage code stays inside `kassensturz-store`, and the trait comes when it is needed). SQLite is the only implementation for v1 (per D-005) and stays the default afterward. **Post-1.0**, other well-known SQL engines (PostgreSQL, MySQL/MariaDB, ...) may be added as further implementations of the same trait — which ones, in what order, and with which Rust driver crate is Q-012. A non-SQLite backend is always an explicit user choice, never a default: it must not weaken the Local-first/Privacy principle (AGENTS.md §2) by pointing at a remote database without the user deliberately setting that up themselves. |
| D-017 | Decided | **A transaction can be broken down into multiple categorized parts, after the fact.** This is the double-entry "split" already named in D-003/§5, surfaced to users under plain language as **Parts** (see `docs/GLOSSARY.md`) — e.g. one €53.20 grocery-store charge becomes €40 Food, €8 Household, €5.20 Fast food. Not limited to import time: any transaction, including ones already imported from a bank, can be edited later to add, remove or resize Parts. Each Part has its own category (optional — not forced) and amount. The editor **auto-calculates one remaining Part's amount** as "total minus what's already entered," so the user is never required to do the subtraction themselves — and saving is rejected unless all Parts sum exactly to the transaction's original amount (Principle 1, Correct money: a transaction can never silently stop balancing). This is pre-1.0 scope. Manual entry only here — it does **not** include deriving Parts from a scanned/photographed itemized receipt (OCR); that's taken up in D-018. Rule actions (D-014) still target the transaction as a whole in v1, not individual Parts (Q-014). |
| D-018 | Decided | **Post-1.0: receipt capture and auto-matching, answering Q-013.** Two entry points share one pipeline: (a) an eventual KassenSturz Android companion app that photographs a receipt, and (b) a desktop-only function that works from an existing scan/photo file (image or PDF) — no Android app required for the second. Both feed one shared engine (OCR extraction, then a deterministic matching heuristic — amount + date-proximity + fuzzy merchant/payee name — that looks for the already-imported bank transaction the receipt belongs to) which then proposes a Parts breakdown (D-017) from the receipt's line items. The match and the proposed Parts are always a **suggestion the user confirms**, never auto-applied — the same "propose, don't silently apply" spirit as AI (§8), even though the deterministic matching path itself isn't AI. The baseline (OCR + heuristic matching) must work fully with AI switched off (D-013); an optional AI-assisted extraction path via `kassensturz-ai` may improve results on messy or handwritten receipts once AI is explicitly turned on, but the feature must never require AI to work. Phone-to-desktop transfer must not become "a hosted cloud or sync service run by the project" (still a listed non-goal, §3.3) — candidates are a local-network pairing (KDE Connect is the obvious prior art) or a simpler user-mediated file drop; see Q-015. The Android app is a **separate native app**, not the Qt 6/Kirigami stack via Qt for Android (see D-019). Formally adding Android to the Portability principle's platform list (AGENTS.md §2) still needs its own maintainer sign-off when this is actually scheduled, not assumed now. |

| D-021 | Decided | **Multiple accounts are managed together in one book, and transfers between the user's own accounts are detected and excluded from income/expense.** Multiple accounts per book is already implied by D-003; this locks in that the UI shows them side by side (an overview/dashboard, see M3 in `docs/ROADMAP.md`), not one account at a time. The more substantial part: when a bank import shows a debit in one of the user's accounts and a matching credit in another of the user's accounts in the **same book**, KassenSturz proposes merging the two into a single double-entry **Transfer** — a transaction whose splits are both real (asset/liability) accounts, with no income/expense category — so moving money between your own accounts never inflates spending or income totals in reports (this follows directly from the existing double-entry model in §5 once a transfer is correctly identified, not a new reporting rule). Matching is by amount (same currency) or a plausible exchange rate for cross-currency transfers (consistent with D-004) + date-proximity + **both accounts already being ones the user added to this book** — external IBANs are never transfer candidates, only accounts KassenSturz already manages for that user. Like Rules (D-014) and receipt matching (D-018), a detected transfer is always a **suggestion the user confirms**, never a silent merge — see Q-019 for whether a "trust this account pair" setting should reduce that friction over time, and Q-020 for the exact matching tolerances. |
| D-022 | Decided | **Post-1.0: Multi-user support.** Introduces **Member** (a person using KassenSturz — e.g. each spouse) as a new concept, distinct from financial **Account**; the two are easy to confuse, so keep them separate in code and docs (see `docs/GLOSSARY.md`). Each Account has an owner Member and can be explicitly shared with other Members; default is private to its creator until shared — mirrors Principle 2 (Privacy/ownership) extended to the household. A Member's view (dashboards, totals, overview) is scoped to Accounts they own plus Accounts shared with them, never the whole book by default. This scoping is enforced **once**, in the data-access layer (`kassensturz-core`/`kassensturz-store`), not reimplemented per feature — Rules (D-014), Parts (D-017), Transfers (D-021) and receipt matching (D-018) all inherit it automatically: both spouses can complete the shared account's imported bills from their own phone's Android app (D-019) because the shared Account is in both of their visible sets, with no special-casing needed anywhere else. Multi-device topology is **a shared host with thin clients** (confirmed by the maintainer over the alternative of independent syncing copies): one device the household itself owns (a desktop, or a home server/NAS) runs the authoritative data store; phones (via the Android app) and other desktops connect to it over the **local network** as thin clients. This is explicitly **not** "a hosted cloud or sync service run by the project" (§3.3) — nothing is hosted by KassenSturz the project; it's infrastructure the household already controls. It still requires network access for thin clients to reach the host, so it must follow hard rule 3.1.4: **opt-in and off by default** — a single-user, single-device install stays exactly as it is today, zero network exposure, unless a person deliberately turns multi-user/sharing on. Builds on D-016's storage-trait work: the concrete host backend for concurrent multi-client access is Q-021. Authentication is a lightweight, local Member-profile pick, not a hardened security boundary against another Member with file access to the same data (same honesty as Q-007's unencrypted-SQLite default) — exact mechanism is Q-023. Transport/protocol for thin clients is Q-022. |
| D-023 | Decided | **Post-1.0 (moved by D-071; a code-only Rule suggestion takes over its most useful part in 1.0): KassenSturz's AI features keep their own local "memory," analogous to this repo's own AGENTS.md/agent-memory setup.** Two parts: (a) a small, maintained **context document** describing this book's own setup (category names, Members/Accounts once D-022 exists, house rules such as "never give investment advice") that's handed to whichever AI the user has connected, so they don't re-explain their own setup every session; (b) a **pattern memory** — structured notes the AI feature accumulates about recurring interactions, e.g. "this payee is often categorized as X" or "this summary is asked for often" — consulted as context in later AI interactions. Both live as ordinary rows in the book's own storage (via `kassensturz-store`, D-016), not separate files on disk, so they travel with normal backups/exports and stay inside the "one file is your whole book" portability promise. The point of pattern memory is to let AI **propose promoting a recurring ad-hoc pattern into a first-class, deterministic feature** — a Rule (D-014) or a saved report — never to become a parallel, AI-only source of authority; this keeps faith with "Numbers come from code" and "AI proposes, the user confirms" (§8). Memory is consulted only when the user is actively interacting with AI — passive, on-demand; v1 does not push unprompted notifications off the back of it (Q-024). Once Members exist (D-022), memory is scoped the same way Account visibility already is — enforced once, inherited automatically, not a separate permission system. Whether/how `kassensturz-mcp` exposes any of this to the user's own external AI tools is undecided (Q-025), as are retention/frequency tuning (Q-026). |

| D-027 | Decided | **Amounts, currencies and rounding.** Amounts are stored as **64-bit integers in minor units**. Cryptocurrencies are not in v1; if they come later, they are tracked like securities, so 64-bit amounts stay sufficient. **ISO 4217** decides how many decimal places a currency has; CLDR is used for display only. Each book **stores the decimal places of every currency it uses**, fixed when that currency is first used, so an update to the app's currency table can never rescale stored amounts; changing them for existing data needs an explicit, tested migration. The default rounding mode is **round half away from zero** ("commercial rounding", answers Q-004); verify it against the EU euro-conversion rules before release. The rounding setting is **stored in the book**, so every computer calculates the same way, and changing it affects **only future calculations**: stored amounts are never recalculated. Exchange rates, prices and quantities are fixed-point decimals (D-051). |

| D-029 | Decided | **v1 feature scope.** In v1: **basic budgets** (a monthly limit per category); **credit card accounts** (AqBanking 6.9.2 implements the FinTS credit card statement job DKKKU, so their transactions can be fetched where the bank offers it, otherwise they come from file import or manual entry); **checking KassenSturz's balance against the bank's balance**; **export** as CSV plus a complete export of the book in an open format; one built-in, plain-language **default category set**, translated. | D-030 | Decided | **Import pipeline.** Steps run in this order: **duplicate check, then Transfer matching (D-021), then Rules (D-014)**. A transaction whose bank-provided transaction ID is already in the book is skipped automatically, and the import summary says how many were skipped; uncertain cases (no ID, or similar but not identical data) are shown to the user to decide. | D-038 | Decided | **A book is open in only one place at a time** (v1). While a book is open, KassenSturz keeps a small lock file next to it with the computer's name and the time. KassenSturz has seven rounding modes, matching the seven rounding strategies of `rust_decimal` (checked against 1.43.0), so calculations with rates and prices (D-051) can use each of them: **half away from zero** (the default), half even (banker's rounding), half toward zero, toward zero, away from zero, floor and ceiling. Every calculation that rounds takes the mode as a parameter and rounds once, at the end; so far that is `Money::checked_mul_ratio`, an amount times a ratio such as 19/100 or 1/3, computed exactly in 128 bits. The book stores its mode in its `settings` row (`docs/BOOK_FORMAT.md`, layout 2), set to the default when the book is created. Which modes Settings offers, and how it explains them, is decided with M3: the everyday-user test (AGENTS.md §6) may leave only the first two visible. |
| D-079 | Proposed | **Exchange rates, prices, quantities and the price table** (applies D-028, D-051). **Numbers:** `ExchangeRate` (above zero), `Price` (zero or above) and `Quantity` (any sign) hold at most **18 digits** (not counting leading zeros) and **18 decimal places**, so a book stores each in two INTEGERs. They keep the decimal places as entered (1.0850 stays 1.0850) and compare by value (1.50 equals 1.5). Text in and out is only the plain form `-?digits[.digits]`; regional formats are the UI's job (D-065). `rust_decimal` holds the value but is private to `kassensturz-core`'s decimal module, and `clippy.toml` blocks its floating-point methods; its `TryFrom<f64>` can't be blocked by path, which the privacy covers. **Conversions** (`Money::checked_mul_rate`, `Money::checked_div_rate`) take each currency with the decimal places the book stores for it (`Currency`), compute in 128-bit integers and round once with the given rounding mode. They don't use `rust_decimal`'s arithmetic, which rounds without saying so past 28 digits. Multiplying fails only if the result doesn't fit into 64 bits; dividing also fails for amounts no household has, e.g. above about 1.7 × 10^16 yen at a rate with 18 decimal places into a currency with 4. **Price table:** one rate per pair of currencies, direction and day; adding a second for the same day is refused so the user changes or removes the first, rather than two rates disagreeing. Converting the other way divides by the same rate, so no inverse is stored. The rate for a date is the newest on or before it, in the direction asked; which direction a conversion looks up first is decided with the parts in other currencies (M1.6, D-043). The source of every rate is recorded; `manual` is the only one in v1 (D-028). Security prices join the table when securities come (D-029). Layout 3 (`docs/BOOK_FORMAT.md`). |
| D-080 | Proposed | **Book files: application ID, lock file, backups and migrations** (applies D-033, D-037, D-038, D-045; M1.3). **Application ID** `0x4B535A42`, the letters `KSZB` for KassenSturz book: neither SQLite's list of application IDs (`magic.txt`) nor `file`'s SQLite magic lists it (checked 2026-10-19, `docs/THIRD_PARTY.md`). The store reads it, and SQLite's header, from a file's first bytes before SQLite opens the file, so another program's SQLite file is never changed, not even its journal mode; a file without it isn't a book, which also turns away the book files tests wrote before M1.3. **Lock file** `<book>.lock`, e.g. `Household.ksz.lock`, a plain name Nextcloud's default exclude list doesn't leave out (it leaves out e.g. `.~lock.*` and `*.part`; checked 2026-10-19). It holds the computer's name, the time in UTC and a random token. It is created only if there is none and removed on closing only while it still holds this KassenSturz's token, so closing a book that was opened anyway elsewhere leaves the new lock alone. Any lock file, even an empty or damaged one, counts. **Opening anyway** after the warning takes over the lock only if it is still exactly the one the user was warned about; otherwise the user is warned about the new one. **Backups** are complete copies made with SQLite's `VACUUM INTO`, written under a `.partial` name, synced to the disk and then renamed, so a file named like a backup is never incomplete; if the backup fails, the book isn't updated. They are named after the book and the time in UTC, e.g. `Household 2026-10-19 11-04-02 UTC.ksz`, since the store has no time zone data (D-061). The last 10 per book name are kept, never removing the one just made; books with the same name in different folders share them. **Migrations** start from an empty database at layout 1 and run in one transaction that also sets the application ID and layout version, with foreign keys off and every reference checked before the commit. **The computer's name and the backup folder** come from the front end (`Computer` in `kassensturz-store`), since finding them differs per platform and belongs in `kassensturz-platform`; the first front end that opens book files is the command-line tool (M1.8). Layout `docs/BOOK_FORMAT.md`. |
| D-081 | Proposed | **Accounts: types, names and closing** (applies D-021, D-029, D-031, D-067; M1.4). **Types:** an account can have a type the user sees: checking, savings, cash or credit card. A type belongs to one kind: the first three are assets (money the user has), a credit card is a liability (money owed, shown as "You owe", D-067). Types exist so later steps know what an account is for: "make it a Transfer" into a cash account (D-031), a bank's credit card statements (D-029). Categories have none; accounts made before layout 4 have none either. Loans and investments get types when they come (D-029). **Names:** an account's name isn't empty and isn't shared by another account, ignoring capitals and spaces around it, closed accounts included, so users can always tell accounts apart; KassenSturz checks this when it writes, the database doesn't. Categories are checked when they become a tree (M1.5). **Closing:** a user can close an account when its balance is zero, so no money is hidden. It keeps its history and its name, takes no new transactions, and drops out of the list of accounts until the user lists closed ones or opens it again. Deleting an account isn't part of M1.4: it needs a decision on what happens to its transactions (M1.6, M1.9). **Migration:** layout 4 adds the two columns `account_type` and `closed` to existing books. It is the first migration that runs on a book that already exists, so it gets a backup (D-080). |
| D-082 | Proposed | **The category tree** (applies D-067; M1.5). Categories stay accounts of kind income or expense (`docs/BOOK_FORMAT.md`), so a transaction's parts refer to them like to any account, and each stores the category it sits inside (`parent_id`), to any depth. **Rules:** a category sits inside a category of its own **kind** (income inside income, spending inside spending) and **currency**, so the total of a category can add up what is inside it without converting; siblings, the categories of one kind inside the same category, never share a name, ignoring capitals and spaces around it, while the same name elsewhere is a different category (Food › Other and Home › Other); a category can't sit inside itself or its own subcategories. Accounts don't sit inside anything. A category can be **moved** with everything inside it and all its transactions, and renamed. The tree is listed in one order: income before spending, each category followed by what is inside it, siblings by name. **Not in M1.5:** deleting or merging categories, because they need a decision on what happens to their transactions (M1.6, M1.9); the built-in default category set, which comes with the first-run flow (M3, D-029, D-067); roll-up totals per branch, which come with reports and budgets (M6). A category in a currency of its own is possible, since every category is an account with a currency (D-027); how a Part in another currency shows up in a category comes with D-043 (M1.6). |
| D-083 | Proposed | **Transactions and Parts** (applies D-017, D-021, D-030, D-043, D-067; M1.6). **Parts without a category:** a part can have no category yet (D-017: the category is optional). It counts in no account's balance, and reports will show it as having no category. An import (M2) adds a bank's entry as the account's part plus one such part, which a Rule or the user then gives a category. **Parts in other currencies (D-043):** a transaction counts in one currency; all its parts' amounts are in it and add up to zero there. A part booked to an account in another currency also keeps its amount in that currency, its foreign amount, which is what the account's balance adds up, so every part is in its account's currency. Both amounts have the same sign. When one amount was calculated from the other with a rate from the price table, the part keeps a copy of that rate with its date and source (AGENTS.md §5), also when the rate is changed or removed later; when both amounts were given, e.g. by the bank or the user, no rate is stored and their ratio is the rate. A part without a category can't be in another currency. **Converting** (the open point of D-079): KassenSturz takes the newest rate on or before the date, in either direction, multiplying by a rate from the amount's currency and dividing by one the other way; if both directions have a rate on that newest day, the one from the amount's currency counts. It rounds once, in the book's rounding mode (D-027). **What a bank or file delivered (D-067)** is kept per part, with the part booked to the account the statement is for, not per transaction, so a Transfer matched from two statements (D-021, M1.10) keeps what both banks delivered, including both IDs for the duplicate check (D-030): the bank's ID for the entry, its booking date and value date (D-030), the other party's name and IBAN (as text and not checked, since it is kept as delivered) and the remittance information. The transaction's own booking date is the one shown; the user can change it, and the bank's dates stay with the part. Transactions entered by hand have no value date. **Changing a transaction (D-017):** it is replaced as a whole, keeping its ID: its date, payee and parts can change, and parts can be added, removed, resized or given another category. The changed transaction must balance like a new one, and KassenSturz calculates the amount of the one part the user leaves open ("total minus what's already entered"). A part a bank or file delivered keeps its account, its amount in that account's currency and its delivered details, so the transaction keeps adding up to what the bank said; only its value in the transaction's currency can change, e.g. when the transaction is made to count in another currency. **Closed accounts (D-081):** no new transaction books to one, and changing or removing an old transaction can't change the total booked to it. **Removing** a transaction is possible, also an imported one; undo comes with the change history (M1.9). **Not in M1.6:** a list of payees (payees stay text), notes on transactions, looking up a bank's ID for the duplicate check (M2, Q-039), and deleting or merging accounts and categories, which can now turn their parts into parts without a category but wait for undo (M1.9, D-081, D-082). Layout 6 (`docs/BOOK_FORMAT.md`). |
