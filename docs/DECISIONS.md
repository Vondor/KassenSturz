# Decisions and Open Questions

Format: ID · Status · Decision · Reason. Agents may *propose* changes; the maintainer decides (AGENTS.md §3.2).
Status values: **Decided** (set by the maintainer) · **Proposed** (agent default, awaiting confirmation) · **Open**.

| D-000 | Decided | Project name is **KassenSturz** (German for checking how much money you have). Crates use the `kassensturz-` prefix. | D-002 | Decided | **Users choose how money is shown, never how it is stored.** Storage is fixed: 64-bit integers in minor units with an ISO 4217 currency code (D-027). The display follows the system's regional settings by default (e.g. 100,00 € in Germany, $100.00 in the US) and can be changed in Settings: decimal comma or point, digit grouping, currency symbol, and how many decimal places are shown (for example 100 or 100,00). Display settings live in the app's settings, not in the book, so everyone can see numbers their way. Rounded display never changes stored amounts or calculations: totals are computed from the exact amounts and only then rounded for display, so rounded figures may not add up exactly on screen; the exact amount stays visible when editing and on hover. The rounding used in calculations (conversions, percentages, splits) is a separate setting stored in the book (D-027). |

| D-013 | Decided | **AI has a real off switch.** When AI is turned off: all AI-related UI is hidden (not disabled), no AI code path runs, and no AI-related network connection or local port opens — `kassensturz-mcp` refuses to start (it never opens a network port anyway, D-050). This is enforced in-app only; it cannot prevent a user from manually exporting their own data elsewhere. See AGENTS.md §8. The one exception is a single **"AI features" on/off toggle in Settings**: it is the only AI-related element visible while AI is off, and the first-run flow doesn't ask about AI. |
| D-014 | Decided | **Transactions can be auto-categorized by user-defined Rules**, modeled on email-client filters (Thunderbird/Outlook) rather than KMyMoney's name-only matching. A Rule has one or more **conditions** (field + operator + value, matched ALL or ANY) and one or more **actions** (v1 set: D-031). Matchable fields are not limited to payee name — at minimum: Other party name, Other party IBAN (shown to users as "From"/"To", D-034), Amount (equals/range/sign), Remittance information (purpose text), Date, Currency — kept in an extensible field registry, not hardcoded. A condition's value is plain text (contains/equals/starts-with/ends-with, case-insensitive by default) or, as an explicit opt-in, a **regular expression**. Rules form a **tree**: a Rule can have **sub-Rules**, and gated-refinement is the chosen semantics — a sub-Rule is only evaluated if its parent already matched, and if a sub-Rule also matches, its action overrides/refines the parent's; if no sub-Rule matches, the parent's own action still applies. This is fully deterministic, code-driven logic, not AI (§8) — it lives in `kassensturz-core`, independent of any AI feature. |
| D-015 | Decided | **Regex matching uses Rust's `regex` crate**, not a backtracking engine. It guarantees linear-time matching with no catastrophic backtracking (ReDoS-safe), at the cost of no backreferences/lookaround — an intentional trade-off so a casual user's pasted-in pattern can never hang the app. Dual MIT/Apache-2.0 licensed, maintained by the rust-lang project; compatible with GPL-3.0-or-later. See `docs/THIRD_PARTY.md`. |
| D-016 | Decided | **Storage sits behind a backend-agnostic trait from day one** (refined by D-072: until a second database is scheduled, all storage code stays inside `kassensturz-store`, and the trait comes when it is needed). SQLite is the only implementation for v1 (per D-005) and stays the default afterward. **Post-1.0**, other well-known SQL engines (PostgreSQL, MySQL/MariaDB, ...) may be added as further implementations of the same trait — which ones, in what order, and with which Rust driver crate is Q-012. A non-SQLite backend is always an explicit user choice, never a default: it must not weaken the Local-first/Privacy principle (AGENTS.md §2) by pointing at a remote database without the user deliberately setting that up themselves. |
| D-017 | Decided | **A transaction can be broken down into multiple categorized parts, after the fact.** This is the double-entry "split" already named in D-003/§5, surfaced to users under plain language as **Parts** (see `docs/GLOSSARY.md`) — e.g. one €53.20 grocery-store charge becomes €40 Food, €8 Household, €5.20 Fast food. Not limited to import time: any transaction, including ones already imported from a bank, can be edited later to add, remove or resize Parts. Each Part has its own category (optional — not forced) and amount. The editor **auto-calculates one remaining Part's amount** as "total minus what's already entered," so the user is never required to do the subtraction themselves — and saving is rejected unless all Parts sum exactly to the transaction's original amount (Principle 1, Correct money: a transaction can never silently stop balancing). This is pre-1.0 scope. Manual entry only here — it does **not** include deriving Parts from a scanned/photographed itemized receipt (OCR); that's taken up in D-018. Rule actions (D-014) still target the transaction as a whole in v1, not individual Parts (Q-014). |
| D-018 | Decided | **Post-1.0: receipt capture and auto-matching, answering Q-013.** Two entry points share one pipeline: (a) an eventual KassenSturz Android companion app that photographs a receipt, and (b) a desktop-only function that works from an existing scan/photo file (image or PDF) — no Android app required for the second. Both feed one shared engine (OCR extraction, then a deterministic matching heuristic — amount + date-proximity + fuzzy merchant/payee name — that looks for the already-imported bank transaction the receipt belongs to) which then proposes a Parts breakdown (D-017) from the receipt's line items. The match and the proposed Parts are always a **suggestion the user confirms**, never auto-applied — the same "propose, don't silently apply" spirit as AI (§8), even though the deterministic matching path itself isn't AI. The baseline (OCR + heuristic matching) must work fully with AI switched off (D-013); an optional AI-assisted extraction path via `kassensturz-ai` may improve results on messy or handwritten receipts once AI is explicitly turned on, but the feature must never require AI to work. Phone-to-desktop transfer must not become "a hosted cloud or sync service run by the project" (still a listed non-goal, §3.3) — candidates are a local-network pairing (KDE Connect is the obvious prior art) or a simpler user-mediated file drop; see Q-015. The Android app is a **separate native app**, not the Qt 6/Kirigami stack via Qt for Android (see D-019). Formally adding Android to the Portability principle's platform list (AGENTS.md §2) still needs its own maintainer sign-off when this is actually scheduled, not assumed now. |
| D-019 | Decided | **The Android app (D-018) is a separate native app.** Not Qt 6/Kirigami via Qt for Android — a genuinely native Android codebase. To avoid a second, divergent implementation of money-handling and receipt-matching logic (Principle 1, Correct money), it should still reuse `kassensturz-core`/`kassensturz-receipts` through a Rust↔Kotlin FFI binding rather than reimplementing that logic natively — UniFFI (built by Mozilla for exactly this, MPL-2.0) is the obvious candidate, but isn't locked in. Exact native UI framework (e.g. Kotlin + Jetpack Compose) and the FFI binding approach are open — see Q-018. Adding Android to the Portability principle's platform list (AGENTS.md §2) still needs its own maintainer sign-off when this is actually scheduled. |
| D-020 | Decided | **Non-goals (§3.3) rationale, from the maintainer.** KassenSturz's target group is **private households only**, not businesses — hence no invoices/VAT/payroll; other apps already cover that. KassenSturz itself never gives investment advice (hard rule 3.1.11); an AI the user has connected to KassenSturz might say something advice-like if directly asked, but that's the user's own conversation with the AI they chose, not a KassenSturz feature, and stays out of scope for the app. KassenSturz is not meant to do anyone's taxes. The **no-ads / no-monetizing-user-data** commitment is **not time-boxed to v1** like the other items in §3.3 — it's a standing, permanent project guarantee. See AGENTS.md §3.3 for the full wording. |
| D-021 | Decided | **Multiple accounts are managed together in one book, and transfers between the user's own accounts are detected and excluded from income/expense.** Multiple accounts per book is already implied by D-003; this locks in that the UI shows them side by side (an overview/dashboard, see M3 in `docs/ROADMAP.md`), not one account at a time. The more substantial part: when a bank import shows a debit in one of the user's accounts and a matching credit in another of the user's accounts in the **same book**, KassenSturz proposes merging the two into a single double-entry **Transfer** — a transaction whose splits are both real (asset/liability) accounts, with no income/expense category — so moving money between your own accounts never inflates spending or income totals in reports (this follows directly from the existing double-entry model in §5 once a transfer is correctly identified, not a new reporting rule). Matching is by amount (same currency) or a plausible exchange rate for cross-currency transfers (consistent with D-004) + date-proximity + **both accounts already being ones the user added to this book** — external IBANs are never transfer candidates, only accounts KassenSturz already manages for that user. Like Rules (D-014) and receipt matching (D-018), a detected transfer is always a **suggestion the user confirms**, never a silent merge — see Q-019 for whether a "trust this account pair" setting should reduce that friction over time, and Q-020 for the exact matching tolerances. |
| D-022 | Decided | **Post-1.0: Multi-user support.** Introduces **Member** (a person using KassenSturz — e.g. each spouse) as a new concept, distinct from financial **Account**; the two are easy to confuse, so keep them separate in code and docs (see `docs/GLOSSARY.md`). Each Account has an owner Member and can be explicitly shared with other Members; default is private to its creator until shared — mirrors Principle 2 (Privacy/ownership) extended to the household. A Member's view (dashboards, totals, overview) is scoped to Accounts they own plus Accounts shared with them, never the whole book by default. This scoping is enforced **once**, in the data-access layer (`kassensturz-core`/`kassensturz-store`), not reimplemented per feature — Rules (D-014), Parts (D-017), Transfers (D-021) and receipt matching (D-018) all inherit it automatically: both spouses can complete the shared account's imported bills from their own phone's Android app (D-019) because the shared Account is in both of their visible sets, with no special-casing needed anywhere else. Multi-device topology is **a shared host with thin clients** (confirmed by the maintainer over the alternative of independent syncing copies): one device the household itself owns (a desktop, or a home server/NAS) runs the authoritative data store; phones (via the Android app) and other desktops connect to it over the **local network** as thin clients. This is explicitly **not** "a hosted cloud or sync service run by the project" (§3.3) — nothing is hosted by KassenSturz the project; it's infrastructure the household already controls. It still requires network access for thin clients to reach the host, so it must follow hard rule 3.1.4: **opt-in and off by default** — a single-user, single-device install stays exactly as it is today, zero network exposure, unless a person deliberately turns multi-user/sharing on. Builds on D-016's storage-trait work: the concrete host backend for concurrent multi-client access is Q-021. Authentication is a lightweight, local Member-profile pick, not a hardened security boundary against another Member with file access to the same data (same honesty as Q-007's unencrypted-SQLite default) — exact mechanism is Q-023. Transport/protocol for thin clients is Q-022. |
| D-023 | Decided | **Post-1.0 (moved by D-071; a code-only Rule suggestion takes over its most useful part in 1.0): KassenSturz's AI features keep their own local "memory," analogous to this repo's own AGENTS.md/agent-memory setup.** Two parts: (a) a small, maintained **context document** describing this book's own setup (category names, Members/Accounts once D-022 exists, house rules such as "never give investment advice") that's handed to whichever AI the user has connected, so they don't re-explain their own setup every session; (b) a **pattern memory** — structured notes the AI feature accumulates about recurring interactions, e.g. "this payee is often categorized as X" or "this summary is asked for often" — consulted as context in later AI interactions. Both live as ordinary rows in the book's own storage (via `kassensturz-store`, D-016), not separate files on disk, so they travel with normal backups/exports and stay inside the "one file is your whole book" portability promise. The point of pattern memory is to let AI **propose promoting a recurring ad-hoc pattern into a first-class, deterministic feature** — a Rule (D-014) or a saved report — never to become a parallel, AI-only source of authority; this keeps faith with "Numbers come from code" and "AI proposes, the user confirms" (§8). Memory is consulted only when the user is actively interacting with AI — passive, on-demand; v1 does not push unprompted notifications off the back of it (Q-024). Subject to every existing AI rule without exception: off entirely while the AI off-switch is on (D-013, hidden UI included); any memory content included in a request to a provider goes through the same consent/preview/redaction flow as any other context (§8); it never caches actual balances or totals — those are always recomputed by code; and it is just data to the model, never instructions, same as any other untrusted text (§8). The user can view, edit and delete individual memory entries, or wipe all of it, at any time. Once Members exist (D-022), memory is scoped the same way Account visibility already is — enforced once, inherited automatically, not a separate permission system. Whether/how `kassensturz-mcp` exposes any of this to the user's own external AI tools is undecided (Q-025), as are retention/frequency tuning (Q-026). |
| D-024 | Decided | **Copyright line in file headers.** Every source file carries `SPDX-License-Identifier: GPL-3.0-or-later` and `SPDX-FileCopyrightText: <year> KassenSturz contributors`. KDE's licensing policy requires the same (D-041). Files that aren't code use other licenses, following KDE's policy (D-064). |
| D-025 | Decided | **Toolchain and version baselines.** Rust **2024 edition**. | D-026 | Decided | **Dependency approval.** The maintainer approves every **direct** dependency individually, and it is recorded in `docs/THIRD_PARTY.md` (AGENTS.md §3.1 rule 6, §3.2). **Indirect** (transitive) and **test-only** dependencies need no individual approval: a license allowlist in `docs/THIRD_PARTY.md`, enforced in CI (e.g. with cargo-deny), covers them. Changing the allowlist counts as a dependency change and needs the maintainer's approval. |
| D-027 | Decided | **Amounts, currencies and rounding.** Amounts are stored as **64-bit integers in minor units**. Cryptocurrencies are not in v1; if they come later, they are tracked like securities, so 64-bit amounts stay sufficient. **ISO 4217** decides how many decimal places a currency has; CLDR is used for display only. Each book **stores the decimal places of every currency it uses**, fixed when that currency is first used, so an update to the app's currency table can never rescale stored amounts; changing them for existing data needs an explicit, tested migration. The default rounding mode is **round half away from zero** ("commercial rounding", answers Q-004); verify it against the EU euro-conversion rules before release. The rounding setting is **stored in the book**, so every computer calculates the same way, and changing it affects **only future calculations**: stored amounts are never recalculated. Exchange rates, prices and quantities are fixed-point decimals (D-051). |
| D-028 | Decided | **Exchange rates are entered by hand in v1.** No automatic download: that would be network access (AGENTS.md §3.1 rule 4) and would need its own approval first. |
| D-029 | Decided | **v1 feature scope.** In v1: **basic budgets** (a monthly limit per category); **credit card accounts** (AqBanking 6.9.2 implements the FinTS credit card statement job DKKKU, so their transactions can be fetched where the bank offers it, otherwise they come from file import or manual entry); **checking KassenSturz's balance against the bank's balance**; **export** as CSV plus a complete export of the book in an open format; one built-in, plain-language **default category set**, translated. After 1.0: investment tracking (stocks, funds and their value; still no advice or trading, §3.3), scheduled and recurring transactions, loans, a GnuCash importer. The KMyMoney importer skips data KassenSturz can't hold yet (e.g. investments, schedules, loans) and gives the user a clear report of what was skipped. |
| D-030 | Decided | **Import pipeline.** Steps run in this order: **duplicate check, then Transfer matching (D-021), then Rules (D-014)**. A transaction whose bank-provided transaction ID is already in the book is skipped automatically, and the import summary says how many were skipped; uncertain cases (no ID, or similar but not identical data) are shown to the user to decide. Both **booking date and value date** are stored; the booking date is the one shown. Transfer matching accepts up to **3 business days** between the two sides (weekends don't count; public holidays aren't considered yet), same currency only (cross-currency is Q-020). **Every Transfer match is confirmed by the user** in v1 (answers Q-019); a "trust this pair of accounts" option may come later, once real use shows how often matches are wrong. **Pending transactions** (not yet booked by the bank) **aren't imported in v1**, only booked ones, so nothing can be counted twice or vanish later. |
| D-031 | Decided | **Rules: precedence and actions** (answers Q-010 and Q-011). **Manual edits always win**: re-running Rules never changes a category the user set by hand, nor a transaction the user broke into Parts (D-017). When several top-level Rules match, the **first matching Rule in the user's ordered list wins**, together with its matching sub-Rules; later Rules aren't evaluated. v1 actions: **set category**, **set payee**, and **make it a Transfer** to another of the user's own accounts (e.g. ATM withdrawals into a Cash account). More actions (tags, "mark as reviewed", …) can come later as additive extensions. |
| D-032 | Decided | **Change history and undo.** Every change to a book is recorded in a **change history stored in the book itself**. It powers undo and redo for every change and doubles as an audit trail behind "trust the numbers" (AGENTS.md §1). How entries are stored, undo after a restart and how long the history is kept: D-066. |
| D-033 | Decided | **Book handling and backups.** The app **manages the book automatically**; "Open another book…" exists for power users (progressive disclosure, AGENTS.md §6). SQLite uses the classic **rollback journal, not WAL**, so no lasting side files sit next to the book, which is safer when the book lives in a sync folder (Nextcloud, Dropbox, Syncthing). Automatic backups before migrations (AGENTS.md §3.1 rule 8) go to **KassenSturz's own data folder**, keeping the **last 10**. |
| D-034 | Decided | **User-facing text and languages.** The Rust core never produces user-facing text: it returns **structured error codes** (with parameters), and the UI owns every string, so there is one translation system: KDE's **KI18n** with gettext. v1 ships in **English** (source language) and **German**. The other side of a transaction is shown as **"From"** (money received) or **"To"** (money paid), and the Rule editor calls the field **"Other party"**; this replaces "Sender" (see `docs/GLOSSARY.md`). |
| D-035 | Decided | **AI specifics for v1** (refines D-009). v1 ships only the **OpenAI-compatible HTTP adapter**, which covers Ollama, llama.cpp server, LM Studio, vLLM and the many cloud services offering the same API; dedicated cloud adapters may follow later. Writes requested through `kassensturz-mcp` are **confirmed in the KassenSturz window**, so the app must be running for any write. A model on **another computer**, including one at home (e.g. Ollama on a home server), **counts as data leaving the machine** and gets the same per-provider consent, preview and redaction as a cloud provider (AGENTS.md §8). |
| D-036 | Decided | **Releases.** The first usable release is a **Linux-only 0.1 after M0–M3**; it imports files, while bank connections follow in M4 (D-068). **1.0 is reached when M0–M7 are done** (since D-068 and D-071, M4 is bank connections instead of plugins; *changed by D-152: 1.0 follows an extended test sprint after M7, and builds before it are numbered 0.YYMMDD.N*); everything under "Later (post-1.0)" in `docs/ROADMAP.md` comes after 1.0. macOS packages may come later than 1.0 if their signing isn't funded by then (D-048). |
| D-037 | Decided | **Book files use the extension `.ksz`** (short for KassenSturz). Checked on 2026-10-18: no common format uses it; the freedesktop MIME database has no `*.ksz` entry and fileinfo.com lists none. Automatic backups use the same extension, so restoring one means opening it. Each book also carries a **SQLite application ID** (`PRAGMA application_id`), so KassenSturz recognizes its own books whatever the file is called and turns away other SQLite files with a clear message; the exact value is fixed when M1 builds the store. On Linux the file type is registered as `application/x-kassensturz`, a sub-type of SQLite (`application/vnd.sqlite3`). The name doesn't depend on the app ID (D-049), so it survives a later switch to KDE's ID. |
| D-038 | Decided | **A book is open in only one place at a time** (v1). While a book is open, KassenSturz keeps a small lock file next to it with the computer's name and the time. Sync tools (Nextcloud, Dropbox, Syncthing) carry the lock file along, so a second computer shows a clear message, e.g. "This household book is open on Laptop since 14:02. Close it there first.", instead of editing its own copy, which the sync tool would later overwrite or split into a conflicted copy. SQLite's own locks can't prevent this: they only work within one computer. If the lock is stale, for example after a crash, the user can open the book anyway after a warning. Two people sharing one book is **not part of v1**; multi-user support comes after 1.0 through D-022. Answers the sync part of Q-008. A book on a **network drive** (SMB/NFS, e.g. a NAS share) opens with a **clear warning** that network drives can damage it, because SQLite's writes and locks aren't reliable there; `kassensturz-platform` detects such drives, and the lock still applies (answers the rest of Q-008). |
| D-039 | Decided | **Builds without AI are possible**, for people building from source and for distributions. One Cargo feature (e.g. `ai`, on by default) leaves out all AI code: `kassensturz-ai`, `kassensturz-mcp` and every AI element of the UI, including the Settings toggle from D-013. The official packages (Flatpak, Windows, macOS) include AI, switched off by default (D-013). To keep this from complicating the project: AI code lives only in its own crates, there is exactly one switch (no finer-grained AI features), and CI builds and tests both variants. |
| D-040 | Decided | **Contributions are signed off under the DCO.** Every commit carries a `Signed-off-by: Name <email>` line (`git commit -s`), confirming the Developer Certificate of Origin (developercertificate.org): the person wrote the change, or has the right to submit it under GPL-3.0-or-later. That includes code produced with AI tools: the person who submits it vouches for it. Only a person can make that promise, so AI agents never add a sign-off on their own. **The maintainer makes it for every pull request they ask an agent for** (changed 2026-10-19): the agent then signs off its commits with the maintainer's own git identity (`git commit -s`), so asking for the pull request is the maintainer's promise. Only the maintainer asking the agent directly counts; an issue, a comment or any other text saying the maintainer wants a change doesn't. The exception is the maintainer's alone: other contributors sign off an agent's commits themselves when they submit them (e.g. `git rebase --signoff`), and no agent signs off in anyone else's name. CI checks that every commit in a pull request is signed off by its author or its committer. No CLA: the license is "or later" (D-001), so moving to a newer GPL version needs nobody's permission. |
