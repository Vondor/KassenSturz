## M1 steps

M1 is done in these steps, one small pull request each. The maintainer can hand an agent a step by its ID ("do step M1.3"). Without such an instruction, take the lowest step that is still `todo` and whose prerequisites are `done`. A step that turns out too big for one reviewable pull request may be split further (M1.6a, M1.6b, …); record the split here.

| Step | Scope | Needs | Status |
|---|---|---|---|
| **M1.1 Currencies and rounding** | Our own ISO 4217 table, committed as data (D-062), which supplies a currency's decimal places when the book first uses it (D-027); rounding modes as explicit code, with the book's rounding setting defaulting to round half away from zero and affecting only future calculations (D-027); property tests for `Money` and rounding (AGENTS.md §9.4) | — | done |
| **M1.2 Rates and prices** | Exchange rates, prices and quantities as fixed-point decimals: `rust_decimal` behind KassenSturz's own types, with its floating-point conversions blocked by a lint (D-051); a dated price table, rates entered by hand (D-028). Adds `rust_decimal` as a direct dependency, approved by the maintainer through D-051 and listed in `docs/THIRD_PARTY.md`; details in D-079 | M1.1 | done |
| **M1.3 Book file and migrations** | Versioned migrations from an empty book (D-045); `.ksz` book files with a SQLite application ID (D-037); rollback journal and automatic backups in the app's data folder (D-033); open in one place at a time via a lock file (D-038); `docs/BOOK_FORMAT.md` updated (D-046). ## M2 steps

M2 is done in these steps, one small pull request each, the same way as M1. The interface and the pipeline come first, because every format builds on them and the pipeline holds the money-critical logic; CAMT.053 then tests the pipeline end to end before CSV, the format most households download; the export comes before KMyMoney, so the work doesn't wait for KMyMoney's sample files. A step that turns out too big for one reviewable pull request may be split further (M2.9a, M2.9b, …); record the split here.

| Step | Scope | Needs | Status |
|---|---|---|---|
| **M2.1 Importer interface** | New crate `kassensturz-import`: the Importer interface as a native Rust trait, which the WASM plugin API mirrors after 1.0 (D-007, D-069, D-071); a statement model independent of the file format: the account it is for (IBAN, currency), its entries with booked or pending status, the bank's ID for each entry, booking and value date, amount, the other party's name and IBAN, the remittance information, and the opening and closing balance (D-030, D-067); the interface also has to fit importing a whole book (KMyMoney, M2.9). Input files are untrusted: limits on size and nesting, and text from them passed on only as data (AGENTS.md §8, D-084). Error codes in `docs/ERROR_CODES.md`; a harness for golden-file tests with synthetic files (AGENTS.md §9). Adds the `Importer` trait, `Statement` and `Entry`, `Limits` checked on every import, exact amount reading, `import.` error codes and golden files per importer under `tests/golden/<id>/`, details in D-091 | M1 | done |
| **M2.2 Import pipeline** | A statement into one account of the book, as one user action that undo takes back as a whole (D-086), which needs a new layout for the action. In the order of D-030: only booked entries; the duplicate check, done by the importer, not the store (Q-039, D-083): an entry whose bank ID the account already holds is skipped and counted, entries without an ID or with similar data are returned for the user to decide; Transfer suggestions (D-087); then Rules on the new transactions only (D-088). Each entry becomes the account's part plus one part without a category (D-083). An import summary; a balance check against the statement's closing balance (D-029); `import` in the command-line tool (D-085). Tested with statements built in code, so it waits for no file format. | **M2.6 OFX** | OFX 1.x (SGML, where tags are often left open) and 2.x (XML) | M2.2, M2.3 | todo |

## How to pick work

1. If the maintainer named a step (e.g. "do step M1.3"), do that step. Otherwise take the lowest-numbered milestone that still has open items, and within it the lowest step that is still `todo` and whose prerequisites are `done`. The one exception: the clickable QML mock of the first-run flow (M1.M) runs alongside M1 (D-068).
2. A step's own pull request sets its status to `done` (and its milestone to `doing`, or to `done` after the last step), so the status is right the moment the pull request is merged.
3. Do not start a milestone that depends on unfinished decisions listed in `docs/DECISIONS.md`. Use the safe default there and mark it.
4. Cross-platform CI should exist before M3 grows large, so problems on lower-priority platforms show up early.
