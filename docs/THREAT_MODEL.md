# Threat model

What KassenSturz protects, from whom, and what stops each attack. Written in M4.0, before any bank code exists (D-056), so the steps of M4 build the protections in from the start instead of adding them later. It covers the book, file imports and bank connections. M5.0 extended it for AI (assets A-9 to A-13, sources X-8 to X-10, threats T-21 to T-35), again before any AI code exists, so the steps of M5 build the protections in from the start. AGENTS.md §8 sets the rules the AI rows rest on; D-168 to D-175 in `docs/DECISIONS.md` are the decisions behind them.

**How to keep it current.** Every pull request that touches the keychain, bank connections, unsafe code, network access, the Flatpak's permissions or AI updates the table in [Threats and what stops them](#threats-and-what-stops-them): the "Where" and "Status" columns, and new rows for threats it finds. Such a pull request is a human gate (AGENTS.md §3.2). Vulnerability reports go through [`SECURITY.md`](../SECURITY.md).

Facts about AqBanking and Gwenhywfar below were read in their 6.9.2 and 5.14.1 sources (the versions KassenSturz pins, `docs/THIRD_PARTY.md`); file names are given so the next agent can check them.

## What we protect

| ID | What | Why it matters |
|---|---|---|
| A-1 | **Banking PIN** (and a chip card's PIN) | With the login name it opens the user's online banking. Some banks let a PIN alone read statements without a TAN (D-057) |
| A-2 | **TANs** | One-time codes. A TAN caught in flight could confirm something the user didn't mean. KassenSturz only reads, but the bank doesn't know that |
| A-3 | **Saved PINs in the system keychain** | Saved only if the user chooses (D-057), in whichever program owns the desktop's Secret Service: KWallet, GNOME Keyring or KeePassXC (D-150) |
| A-4 | **Bank login data**: bank code, login name, customer ID, bank server address, TAN method | Not secret on its own, but the login name is half of a login. Treated as personal data |
| A-5 | **Fetched balances and statements** | The household's financial life |
| A-6 | **The book** | Everything the household recorded; it may sit in a sync folder (D-033, D-038) |
| A-7 | **AqBanking's own folder**: its settings (A-4, the accounts' IBANs, the bank's parameters) and its message logs (A-5 in plain text) | Lies outside the book, so it's easy to forget |
| A-8 | **Correct numbers** | Principle 1: a fetched transaction must never be changed, counted twice or lost on the way into the book. With AI: a figure in an answer must come from code, never from a model (D-052) |
| A-9 | **Provider API keys** | A cloud provider's key lets whoever holds it use, and pay for, the user's account. Secret like a PIN (AGENTS.md §3.1 rule 7); kept only in the keychain (D-169) |
| A-10 | **What a model is shown**: the request, the results of the functions it calls, the precomputed overview | It is A-5 and A-6 in a new place. When the model runs on another computer, the data has left the machine (D-035) |
| A-11 | **AI settings and the consent record**: whether AI is on, which provider, which statement of "what is sent" the user agreed to | If someone else can change them, data goes where the user never agreed. They belong to this computer, not to the book (D-168) |
| A-12 | **Change sets and the history** | AI-prepared changes to the book; the user's confirmation is the only thing between a model's idea and the user's numbers (D-047) |
| A-13 | **The debug log and issue drafts** | Describe what the app did, and leave the computer in the user's browser if the user files an issue (D-173) |

The FinTS product registration number (D-058) is **not** a secret: open-source programs carry theirs in the source code. It is protected by D-058's rule that nobody else's number is used, not by hiding it.

## Who and what we defend against

| ID | Attacker or source | Examples |
|---|---|---|
| X-1 | **Data from outside**: the bank's messages, statement files, KMyMoney files | A payee name with HTML in it, a malformed statement, a file built to crash the reader |
| X-2 | **Someone on the network** between KassenSturz and the bank | Public Wi-Fi, a malicious proxy, a fake certificate |
| X-3 | **Someone with a copy of the book or a backup** | A sync server (Nextcloud, Dropbox), a lost USB stick, a shared backup |
| X-4 | **Other user accounts** on the same computer | A shared family computer |
| X-5 | **Other programs running as the same user** | Malware, a browser exploit, another app with broad permissions |
| X-6 | **The supply chain** | A Rust crate, a bundled C library, the Flatpak build |
| X-7 | **Leaks while building and supporting KassenSturz** | A bug report with a real log, a test fixture made from real data, a prompt to an AI agent |
| X-8 | **A model's output**: wrong, invented, or steered by text it was shown | An invented balance, a function call the model was talked into, a link or image in an answer |
| X-9 | **The provider and the path to it** | A cloud service that keeps requests, an Ollama on a home server, someone on the same network, a reply built to exhaust memory |
| X-10 | **Programs that talk to the AI side of KassenSturz** | An AI tool the user connected to `kassensturz-mcp`, another program of the same user writing into its channel (X-5) |

**What we can't stop (X-5).** A program that runs as the user can read the user's files, and can read an unlocked keychain through the Secret Service. KassenSturz limits what such a program can find (no secrets in files, PINs only saved when the user chooses, AqBanking's logs removed), but it can't defend against it. A Flatpak or other sandbox around the other program is what helps there. The same goes for someone with full access to the unlocked computer.

## Where data crosses boundaries

```
 User ─── QML screens (kassensturz-ui-bridge) ──── never sees a PIN or TAN
              │
              │ amounts as text (D-065), bank text as plain text (T-08)
              ▼
     kassensturz-bank (safe Rust) ──── kassensturz-pipeline ──── kassensturz-store ──── book (A-6)
       │      │    PIN modes (D-057), exact amounts (T-10)    import pipeline (D-030)
       │      │
       │      └── kassensturz-platform ──── Secret Service (D-Bus) ──── KWallet / GNOME Keyring (A-3)
       │
       │ only place with unsafe code (D-060)
       ▼
     kassensturz-aqbanking-sys ── loaded at runtime ──► libaqbanking, libgwenhywfar (C)
                                                        │      │
     KassenSturz's small C++ library (Q-035) ──► libgwengui-qt6: setup, PIN and TAN dialogs
                                                        │
                                                        ├── its own folder: settings, message logs (A-7)
                                                        └── TLS (GnuTLS) ──► the bank's FinTS server (X-2)
```

```
 book (A-6) ── kassensturz-store ── kassensturz-ai-tools ── the fixed list of read functions (T-23),
                                         │                   change sets (T-27)
                                         │ results marked as data (T-21), figures exact (T-26)
                     ┌───────────────────┴──────────────────┐
                     ▼                                      ▼
   kassensturz-ai (chat, consent, preview)         kassensturz-mcp (stdio only, T-32)
        │  AI settings and consent: app config           ▲ started by the user's AI tool
        │  outside the book (T-24); key: keychain (T-25)  │ writes: channel to the running app (T-32)
        ▼
   HTTP client + TLS ──► the provider: this computer, or another computer = data has left (T-22, T-30)
```

Trust boundaries: everything the bank, a file or AqBanking returns is **untrusted input** (X-1), checked in `kassensturz-bank` before it reaches the pipeline. Everything that leaves the computer leaves through AqBanking, to the bank the user set up, when the user asks for it. From M5 the second way out is the HTTP client of `kassensturz-ai`, to the provider the user set up and agreed to, only while AI is on (T-13, T-22). Everything a model returns is untrusted too (X-8): it is shown as plain text and acts only through change sets the user confirms (T-27, T-34).

## Threats and what stops them

Status: **planned** (the step named under "Where" builds it), **done** (merged, with a test), **open** (a known gap), **accepted** (a risk we live with, explained).

| ID | Threat | What stops it | Where | Status |
|---|---|---|---|---|
| T-01 | **The PIN is written to disk** by Gwenhywfar or AqBanking. Gwenhywfar can keep passwords in a password-store file (`src/gui/passwdstore.c`, used when the app sets one) and ask to save them for good (`GWEN_GUI_FLAGS_PERMPASSWORDS`) | KassenSturz never gives Gwenhywfar a password store and never sets that flag. Its Gwenhywfar GUI answers every password request itself (`CppGui::getPassword`) with the choices of D-057: ask, remember until the app closes, or the keychain through `kassensturz-platform`. | T-02 | **The PIN or a TAN shows up in a log, an error, a panic message or a crash report** | The PIN type has no `Debug` or `Display` that shows its value and is wiped from memory when dropped (`zeroize`, if approved). | T-04 | **A saved PIN is read by another program** (X-5) | Saving is opt-in; the default is to ask each time (D-057). Saved PINs can be removed in Settings and go with the bank login. Sandboxed apps need explicit permission to reach the Secret Service | M4.1, M4.6 | accepted for unsandboxed programs (see X-5) |
| T-05 | **A wrong saved PIN locks the bank login**: banks block a login after a few wrong PINs, and an app that retries a stored wrong PIN uses them up | When the bank says the PIN is wrong (Gwenhywfar's `setPasswordStatus` "bad"), KassenSturz forgets the remembered PIN and deletes the saved one at once, and never sends a PIN again without asking the user (D-140) | M4.3, M4.5 | **in part**: `PinSession::rejected` forgets the remembered PIN, deletes the saved one and answers "ask" until the user types one (M4.3, tested); M4.5 wires `setPasswordStatus` to it: `Handler::rejected` makes the backend call `PinSession::rejected` and fail with `bank.pin-rejected` (tested with the stub's bad-PIN scenario) |
| T-06 | **AqBanking's message logs keep the user's statements in plain text.** AqBanking 6.9.2 writes every FinTS message it sends and receives to `<its folder>/backends/aqhbci/data/banks/<country>/<bank code>/logs/*.log`, always, with no switch to turn it off (`msglayer/dialog.c`, `msglayer/message.c`). It blanks the PIN and TAN (segments `HNSHA`, `HKPAE`, `DKPAE`), but balances, transactions, IBANs and the login name stay readable | KassenSturz gives AqBanking a folder of its own inside KassenSturz's data folder, readable only by the user, and deletes the `logs` folders after every bank session and at every start, which also catches a crash (D-139). Asking AqBanking's developers for a switch is a follow-up | M4.5 | done: `delete_message_logs` removes every `logs` folder below the bank data at open and after every call, also a failed one (M4.5, tested with the stub's fake log) |
| T-07 | **AqBanking's settings with the login data (A-4) and IBANs are read by others** (X-3, X-4), or mixed up with KMyMoney's or GnuCash's | Its own folder (T-06), created readable only by the user, never inside a sync folder and never in the book. KassenSturz never uses the shared `~/.aqbanking` of other programs (D-139) | M4.5 | done: the backend opens AqBanking on the folder the app gives (below KassenSturz's data folder, M4.5) and never on `~/.aqbanking`; the login name is read from no file |
| T-08 | **Text from a bank or a file is shown as rich text.** Qt Quick shows a text that looks like HTML as rich text unless told otherwise, and rich text can load images from the web. A payee name like `<img src="https://…">` would make KassenSturz contact a server (privacy leak, tracking) or show something that looks like part of the app. In the M3 screens, several labels show such text without `textFormat: Text.PlainText`, for example the payee names in `TransferPrompt.qml` and the row titles in `TransactionRow.qml`. Today the Flatpak has no network, but bank connections need it (D-142) | Every text that comes from a bank, a file or the user is shown with `textFormat: Text.PlainText`. The QML engine gets a network access factory that refuses every non-local address, so even a missed label can't reach the network (D-143). Kirigami's messages have no such setting, so a sentence with outside text in it goes through `Plain.plain()`. Both land before the Flatpak gets network access | M4.T, before M4.8 (`plain_text_audit.rs`, `network_guard.rs`) | **done** |
| T-09 | **Malformed bank data crashes KassenSturz or corrupts memory** (X-1) through the C libraries | Unsafe code lives only in `kassensturz-aqbanking-sys` (D-060). `kassensturz-bank` checks every pointer for null, copies every string at once with a length limit, checks that text is valid UTF-8 (with one written rule and a test for text that isn't), and refuses a statement that is too large, the same limits as for files (D-091). Tests feed the safe layer broken data through a stub library | M4.2, M4.5 | done: the session copies every text through `copy_text` (null-checked, at most `MAX_TEXT_BYTES`, lossy UTF-8), reads every record field by field and frees what it was given; the stub's broken scenarios (text over the limit, non-UTF-8 bytes, missing currency, dates and amounts) are tested in both crates (M4.5) |
| T-10 | **An amount from the bank is changed on the way in**: AqBanking keeps amounts as exact fractions (`AB_VALUE`, GMP rationals in `types/value.c`) but also offers them as floating point (`AB_Value_GetValueAsDouble`, `AB_Value_toDbFloat`, `AB_Value_fromDouble`) | KassenSturz reads amounts only as the exact fraction (`AB_Value_GetNumDenomString`) and turns them into `Money` only when they fit the currency's minor units exactly; anything else is refused with an error code, never rounded (AGENTS.md §3.1 rule 1, D-141). The floating-point functions and the lossy `long` accessors `AB_Value_Num` and `AB_Value_Denom` are left out of the generated bindings, so no code can call them (M4.2, checked by `generate.sh`) | M4.2, M4.3, M4.5 | **in part**: `FetchedAmount::money` turns the fraction's text into `Money` only when it is whole minor units, else `bank.inexact-amount` (M4.3, tested); M4.2 leaves the floating-point functions out of the bindings; M4.2 part done |
| T-11 | **A fetched transaction is counted twice or lost** (A-8) | Fetched statements go through the same pipeline as files: duplicate check by the bank's transaction ID, user decisions for unsure cases, booked transactions only (D-030); the balance check against the bank's balance shows any gap (D-029). Tests feed the pipeline the fake bank's real output, not hand-built values (AGENTS.md §9.4) | M4.3, M4.7 | **in part**: the fake bank's statements go through `import_statements` in `kassensturz-bank`'s tests: pending left out, a second fetch gives duplicates by bank ID, the balance check runs (M4.3); the screen comes in M4.7 |
| T-12 | **A network attacker reads or changes the bank traffic** (X-2) | FinTS with PIN/TAN relies on TLS, which Gwenhywfar does with GnuTLS. KassenSturz's Gwenhywfar GUI accepts certificates that check out and refuses all others without offering "connect anyway" (`checkCert`, D-140), so a fake certificate can't be clicked through; Gwenhywfar 5.14.1 doesn't do this itself (it ignores its own certificate flags and asks for every certificate), so `kassensturz-gwengui` decides, with a test (M4.2). Bank addresses come from the bank list or the user's setup and must start with `https://` | M4.2, M4.5, M4.6 | **in part**: the session's `checkCert` accepts a certificate only when Gwenhywfar marks it error-free with every flag OK and refuses every other with `GWEN_ERROR_SSL_SECURITY`, which the backend turns into `bank.untrusted-server` (M4.5, tested with the stub's bad-certificate scenario); the dialogs of M4.6 must not add a "connect anyway" |
| T-13 | **KassenSturz contacts something other than the user's bank** | Only `kassensturz-bank` opens network connections, only through AqBanking, and only when the user asks to fetch (AGENTS.md §3.1 rule 4). The QML engine refuses remote addresses (T-08). Once the Flatpak has network access (D-142), this rests on the code, so a test checks that nothing but the bank backend asks for the network. *M5.0:* from M5.2 there are exactly two ways out, the bank backend and the AI adapter in `kassensturz-ai` (D-175); the test is extended in M5.2 to allow those two crates and nothing else, and `kassensturz-mcp`, which carries `rmcp` and `tokio` with networking compiled in (Q-123), is allowed those crates only: the test in M5.6 fails if the binary enables a network transport of `rmcp`, names a listening or connecting API, or holds a socket when it runs | M4.5, M4.8, M5.2 | **done** in M4.8, extended in M5.2: `crates/kassensturz-bank/tests/network.rs` fails when a Rust, C++ or QML file outside the QML engine's refusing network manager and three named files of `kassensturz-ai` (its address check and two fake servers of its tests) names a way to connect (`std::net`, Qt Network, `XMLHttpRequest`, WebSockets, …), or when `Cargo.lock`'s dependency graph reaches a crate that opens connections from any KassenSturz crate other than `kassensturz-ai` (D-185) |
| T-14 | **KassenSturz could move money** | It has no code that starts a transfer, standing order or direct debit (D-053). `kassensturz-bank`'s trait has no such function, and the bindings declare only the functions that reading and setting up a login need: the 20 payment commands of `AB_TRANSACTION_COMMAND` and the setters only they use are left out (M4.2, checked by `generate.sh`) | M4.2, M4.3 | **in part**: the `Bank` trait has no function that moves money (M4.3); the bindings come in M4.2; M4.2 part done |
| T-15 | **Key files outside the keychain** | Only PIN/TAN and chip-card logins are offered (D-059). | T-16 | **A malicious or broken library in the bundle** (X-6) | Bundled sources are pinned by SHA-256 and listed in `docs/THIRD_PARTY.md`, checked against two independent copies where possible (the upstream tarball and a distribution's). The bindings are generated by a developer and committed, so a normal build runs no generator (D-060) | M4.2, M4.8 | **done** in M4.8: the Flatpak's four bank modules are upstream tarballs pinned by SHA-256, checked against Ubuntu's copies, which are their mirrors; their command-line tools are removed, and CI checks what the bundle holds |

| T-18 | **Real bank data leaks while building or supporting KassenSturz** (X-7) | Tests use the fake bank and SWIFT's example IBANs only (D-055). The maintainer runs the real-bank test on their own computer, scrubs the log and reports in words; no agent sees bank traffic, logs, PINs or TANs, and no remote session is used for it. `SECURITY.md` asks reporters for made-up data | M4.3, Phase 2 | **in part**: the fake bank with SWIFT's example IBANs (M4.3); the maintainer's own test in Phase 2 |
| T-19 | **Data in the book is read by someone with a copy** (X-3) | The book holds no secrets: no PIN, no TAN, no login name (D-139, Q-086). | T-20 | **Bank text tricks a person or an AI** (X-1): a payee name that reads like an instruction | Text from banks and files is data, never instructions (AGENTS.md §8). For an AI: T-21 to T-27 | M5 | **in part**: the person side is done with T-08; the AI side is split into T-21 to T-27, planned in M5 |

## Rules for code that touches secrets

For the agents of M4.1 to M4.8 and everyone after them:

1. A PIN, TAN or keychain value never goes into a log, an error, a `Debug` or `Display` output, a QML property, a test fixture, a commit or an issue.
2. Secrets live in one type that wipes itself; copies are avoided, and every copy is wiped too.
3. Nothing is written to disk that holds a secret, except through `kassensturz-platform` into the system keychain.
4. Everything from AqBanking, a bank or a file is untrusted input, checked once at the boundary.
5. Amounts are exact: no floating point anywhere between the bank and the book.
6. A step that changes any of this updates this document in the same pull request.

## Rules for AI code

For the agents of M5.1 to M5.13 and everyone after them:

1. Code that reaches a model reads the book only through the functions of `kassensturz-ai-tools`, and a new function needs a row in this document first (T-23).
2. A text from the book, a file, a bank or a model is data. It is delimited and marked wherever it goes into a prompt, and shown as plain text wherever it comes out (T-21, T-34).
3. A provider key is a `Secret`, kept in the keychain only, and never goes into a request preview, a log, an error, a result or a prompt (T-25).
4. AI settings and consent are read from the config file outside the book, and every entry point checks the AI switch first (T-24, T-28).
5. Nothing a model says is applied, sent or paid without the user's confirmation, and no code can send money (T-27, T-29).
6. Every figure in an answer comes from a function (T-26).
7. A step that changes any of this updates this document in the same pull request.
